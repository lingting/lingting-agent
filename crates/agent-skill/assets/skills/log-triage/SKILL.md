# 目标

把一次线上故障从「日志很多」收敛到「一句话结论 + 一条可复现的路径」。

# 输入

- 故障时间窗（精确到分钟）。
- 受影响的接口或客户端标识。
- 已知的变更清单（发布、配置、依赖升级）。

# 定时间窗

先按时间窗切片，不要一上来就全量检索：时间窗过大时相关行会被无关行淹没。
切片粒度从「小时」开始，命中异常后再收敛到「分钟」。

# 收敛故障域

按三个维度收敛：请求入口、下游依赖、数据写入。
每个维度只看两类行：错误与超时。没有这两类行的维度直接排除，不要继续读。

# 判据

- 同一请求标识在多个维度同时出现错误：以下游依赖为第一嫌疑。
- 只有写入维度出现超时：先查连接池与锁等待。
- 三类维度都没有错误行：故障在日志之外（网络、客户端、配置下发），此时停止读日志。

# 升级路径

收敛到单点后仍然无法解释现象时，按以下顺序升级：查指标 → 查链路追踪 → 找变更清单。
不允许在没有判据的情况下猜测原因，也不允许把「可能」写成结论。

# 报告模板

1. 结论：一句话，写明现象、受影响范围与根因所在层。
2. 证据：三条以内，每条都要能指向具体日志行或指标。
3. 复现：最小复现路径。
4. 待办：需要补的监控项。

# 常见误判

- 把「最后一条错误」当根因：它常常是级联失败的结果。
- 把重试全部算成独立错误：应先按请求标识聚合，再看重试次数。
- 只看服务端日志：客户端超时往往先于服务端报错。
- 用行数多少判断严重程度：错误行的数量与影响范围没有必然关系。
