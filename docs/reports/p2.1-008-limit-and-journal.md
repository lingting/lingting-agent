# P2.1-008 许可与写路径复核（H-3）

- **阶段**：P2.1（Batch B）
- **任务**：P2.1-008
- **前置**：P2.1-003（指标）、P2.1-004 ~ 007（已修项先排除）
- **结论**：**两条都不改**。默认配置下的全局 Run 许可不是瓶颈（没有出现 1s 级排队，唯一长排队来自人为把许可配成 1 的用例）；journal 逐帧 `flush` 不是瓶颈（100 帧、单帧最长 0ms，50ms 阈值零触发）。本任务不动任何并发配置默认值（归 P2.1-015）。

---

## 一、许可（`max_concurrent_runs`）

### 数据

| 口径 | 数据来源 | 结果 |
|---|---|---|
| 默认配置（4 个许可）的排队 | 全量 `make test ARGS="--all"` 里所有服务端 `server.log`（`warn` 级） | **零条** `Run 排队过久`（≥1s）；`Run 排队等待超过阈值`（≥100ms）属 `debug` 级，默认不可见 |
| 人为饱和（`max_concurrent_runs = 1`） | `make test ARGS="run.concurrency"`（该用例服务端用 `trace`） | 1 条 `WARN agent_runtime::metrics: Run 排队过久，全局并发许可已饱和 waited_ms=3137` |
| 同时在跑的 Run 数 | `probe.health` 的 `runningRunCount`（P2.1-003 起复用） | 未超过许可数，未出现排队堆积 |
| 整轮耗时 | 全量墙钟 | 33~35s；`--concurrency 4` 与默认 18 的墙钟相同（P2.1-001 已记录 33.9s vs 34.0s） |

### 结论与理由

1. **不是瓶颈**：默认 4 个许可下没有任何一次排队跨过 1s；唯一 3.1s 的排队是「许可故意配成 1」的用例，属配置产物而非默认值问题。
2. **不调默认值**：把许可调大不会让全量更快（并发 4 与 18 的墙钟相同，说明阻塞不在许可上），却会放大上游并发。数值与语法调整统一归 P2.1-015，其硬前置是 P2.1-013。
3. **剩余缺口**：本机跑不进 `debug` 级服务端日志（测试服务端固定 `--log-level warn`），因此默认配置下的排队**分布**只有「全部 < 1s」这个上界，具体百分位缺失。若要补，需要一次 `debug` 级诊断跑（不在 `make test` 路径上）。

## 二、journal 写路径（逐帧 `flush`）

### 数据

| 口径 | 数据来源 | 结果 |
|---|---|---|
| 单帧写入耗时 | 「观测数据」的「事件落盘」行（进程内装配的运行时） | 100 帧，单帧最长 **0ms**，累计 < 1ms 级 |
| 50ms 慢帧阈值 | 全量所有服务端 `server.log` | **零条** `事件文件单帧写入过慢` |
| 事件流规模更大的路径 | `run.journal_consistency`、`session.stream_terminal`、`runtime.journal` 的 80 帧慢客户端用例 | 全部通过；seq 连续、先落盘再转发 |

### 结论与理由

1. **不是瓶颈**：单帧耗时在毫秒刻度以下（本机页缓存吞掉了 `flush`），叠加 100 帧也只在 1ms 量级，没有出现「逐帧 flush 拖慢转发」的迹象。
2. **不做有界批量 flush**：批量 flush 会改变「先落盘再转发」的边界（一次失败回滚多帧、事件可见性延后），在没有任何慢帧证据的前提下属于过度设计。若将来真实磁盘或网络文件系统上出现 50ms 级慢帧，再做批量 —— 阈值日志已经把观测点留在原地。
3. **回归口径**：本任务没有代码改动，因此不存在「修复前后对照」。

## 四、注意点

1. **两个「不是瓶颈」都基于本机 Mock**：Mock Provider 无网络延迟、事件文件在本地磁盘。真实 Provider 下许可会变成真实排队（限额与延迟都在上游），届时需要重跑本节口径。
2. **默认值会放大上游并发**：`3C` 在本机 18 核是 54（P2.1-015 的目标默认值），报告里必须把换算后的数值与上游配额风险一起记录；本次只给「默认 4 不是瓶颈」的结论，不构成「调大也安全」的证据。
