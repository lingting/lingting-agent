# P2.1-003 服务端并发可观测性

- **阶段**：P2.1（Batch A）
- **任务**：P2.1-003
- **执行日期**：2026-11-21
- **结论**：观测点已落齐，默认并发下可读出「同时在跑 Run 数 / 排队时长 / 清理链耗时 / 通道满次数 / `session_locks` 条目数 / 取连接等待」。实测结果指向：当前并发压力**不来自服务端串行点**，唯一观测到的真实排队是 `max_concurrent_runs = 1` 的人为配置。

---

## 一、观测点

| # | 位置 | 指标 | 阈值与级别 |
|---|---|---|---|
| O-1 | `agent-runtime/src/limit.rs::acquire` | 排队次数、排队累计 / 最长时长、超时次数、取消次数、排队水位、执行水位 | ≥100ms `debug`、≥1s `warn`，带 `run_id` |
| O-2 | `manager-agent/src/runtime/session.rs::stop` | 四阶段耗时：数据库落终态 / 执行队列收尾 / 写者收尾 / 合计 | 合计 ≥500ms `warn`，带 `session_id` 与三段分解 |
| O-3 | `manager-agent/src/runtime/handler.rs::process` | 处理链次数、耗时、并发水位、清理客户端数 | 单次 ≥500ms `warn`（含等 `CHAIN` 锁的时间） |
| O-4 | `manager-agent/src/runtime/journal.rs::append` | 落盘帧数、累计 / 单帧最长耗时 | 单帧 ≥50ms `warn`，带文件路径 |
| O-5 | `manager-agent/src/runtime/registry.rs::forward` | 下行通道满 / 已断导致事件被丢弃的次数 | 只计数（丢弃本身按「流已废」处理，是设计语义） |
| O-6 | `manager-agent/src/runtime/registry.rs::session_lock` | 会话锁表条目数（当前与观察到的最大值） | 只计数 |
| O-7 | `lib-db/src/transaction.rs::begin` | 取连接次数、累计 / 最长等待 | ≥100ms `debug`、≥1s `warn`（`lib-db` 为此新增可选依赖 `tracing`，D-P2.1-009） |

实现约定：

- 全部是 `std::sync::atomic` 累加，不新增配置项、不新增 HTTP 接口。
- **采集放在 `metrics` 特性下**（D-P2.1-008）：`bin-agent → lib-bin-web → {agent-runtime, manager-agent} → lib-db` 逐级透传，`bin-tests` 直接依赖 `manager-agent/metrics`。正式构建（`make build` / `make release`）是空实现，不占静态内存、不做原子操作、不编 `tracing`。
- 阈值一律**先比较再构造日志参数**：热路径（每帧落盘、每次取锁、每次转发）只付几次原子加；慢帧才付一次 `path.display()`。
- 水位（正在执行 / 正在排队 / 正在清理）用守卫的 `Drop` 回落，异常路径与 panic 展开也会回落。
- 新增日志默认 `debug`，跨阈值才升 `warn`；`warn` 自带 `run_id` / `session_id` / 文件路径，可单独归因。
- **指标不进标准输出**：运行结束后由测试报告输出（`target/tests/<run>/README.md` 的「观测数据」一节），见 `crates/bin-tests/src/observability.rs`。
### 读取路径

| 场景 | 读取方式 |
|---|---|
| 测试进程内装配的运行时（`manager_agent::assemble_with`，`runtime.*` / `journal.*` / `occupancy.*` / `disconnect.*` / `shutdown.*` 用例） | `manager_agent::runtime::metrics::snapshot()`，由 `bin-tests` 渲染进测试报告的「观测数据」一节 |
| 服务端是子进程（共享 / 隔离 / 自管用例） | 子进程日志按阈值汇总。`warn` 级在所有用例都可见；`debug` 级只在 `--log-level debug`/`trace` 的服务端可见（如 `run.concurrency` 用 `trace`） |
| Run 排队水位 | `probe.health` 的 `runningRunCount`（既有接口，未改契约） |

读取边界：`Server::stop` 是 `start_kill`，子进程没有优雅关闭路径，因此**子进程的指标无法进程内读取**，只能靠日志。

## 二、实测（默认并发 18，73 个用例，`make test ARGS="--all"`，墙钟 36s）

`make test ARGS="--all"` 跑完后，测试报告 `target/tests/<run>/README.md` 的「观测数据」一节（统计范围是本测试进程内装配的运行时）：

```text
### 运行时指标（P2.1-003）

| 指标 | 值 |
|---|---|
| 断连清理链 | 22 次，最长 15ms，并发水位 2，清理客户端 10 |
| 会话停止 | 11 次，最长 15ms（库 30ms｜执行队列 0ms｜写者 2ms） |
| 事件落盘 | 100 帧，最长 0ms |
| 下行通道丢弃 | 1 次 |
| 会话锁表 | 2 条，观察到上限 6 条 |
| 取数据库连接 | 3 次，最长 0ms |
```

| 指标 | 值 | 读法 |
|---|---|---|
| 清理链 | 22 次，最长 13ms，并发上限 2（含等锁），清理客户端 10 | 全局 `CHAIN` 锁**确实产生了排队**（`concurrent_max = 2` 说明有一次在等锁），但等锁时长在 13ms 内 |
| 会话停止 | 11 次，最长 12ms；库 19ms 累计、执行队列 0ms、写者 2ms | 收尾等待在进程内路径上是 0ms——没有 Run 在跑，`executor.stop` 直接返回 |
| 事件落盘 | 100 帧，单帧最长 0ms | 逐帧 `flush` 不是瓶颈（本机页缓存） |
| 下行丢弃 | 1 次 | 有一次写入落在没有下行流的客户端上（用例主动断流），属设计语义 |
| 会话锁表 | 当前 2 条，观察到上限 6 | 进程内用例共建了 6 个会话，条目数与历史会话数同向增长——H-4 的形态成立 |
| 取连接 | 3 次，最长 0ms | 事务很少且不排队 |

### 唯一观测到的真实排队

`run.concurrency` 用 `trace` 级服务端 + `max_concurrent_runs = 1`，第二个 Run 排队后被 O-1 抓到：

```text
WARN agent_runtime::metrics: Run 排队过久，全局并发许可已饱和 run_id="249913309292269568" waited_ms=3148
```

- 这是**人为配置**（1 个并发位）下的排队，不是默认配置下的排队。
- 它在默认并发全量运行里是**唯一**一条 `Run 排队过久` 记录：共享服务端（默认 4 个许可）与其他自管用例都没有触发 1s 阈值。
- 其余阈值日志（`停止运行时会话耗时过长` / `事件文件单帧写入过慢` / `断连清理链单次耗时过长`）在整轮全量里**一条都没有出现**，包括所有子进程服务端的日志。

## 三、偏差与未覆盖项

| 项 | 说明 |
|---|---|
| 取连接计时的位置 | 任务书写的是 `lib-db/src/pool.rs`，实际事务入口是 `lib-db/src/transaction.rs::begin`（`pool.rs` 只有 `open` / `migrate`）。按代码落点。 |
| `lib-db` 的日志依赖 | 为让阈值日志落地，`lib-db` 新增可选依赖 `tracing`（只在 `metrics` 特性下编译，正式构建的 `cargo tree -p lib-db` 里不出现），按 D-P2.1-001 的流程登记为 D-P2.1-009。 |
| 共享服务端的 `debug` 指标读不到 | 测试服务端固定 `--log-level warn`，O-1 的 100ms 级排队分布因此只在 `run.concurrency`（`trace`）里可见。**默认配置下的排队分布本轮只有上界结论**：全部 < 1s，具体数值需一次 `debug` 级的诊断跑（不在 `make test` 路径上）。 |
| 子进程指标无法进程内读取 | `Server::stop` 是 `start_kill`，没有优雅关闭路径，因此子进程指标不能"退出时落一条汇总"。这是 Batch A 只做日志汇总的原因。 |

## 四、对 H-3 / H-4 的初步读数（结案属 P2.1-008）

- **H-3（全局 Run 许可是否瓶颈）**：在本机默认并发下，共享服务端没有出现 1s 级排队；唯一的 3.1s 排队来自把许可配置成 1 的用例。**倾向「默认值 4 不是瓶颈」**，但缺 `debug` 级的排队分布，P2.1-008 需要补。
- **H-3（journal 逐帧 flush 是否瓶颈）**：100 帧落盘、最长 0ms，`warn` 阈值（50ms）零触发。**倾向「不是瓶颈」**，同样需要 008 用更长的事件流复核。
- **H-4（会话锁表只增不减）**：条目数 2 / 峰值 6，与进程内建立的会话数同向。条目数只增的形态**确认成立**，但它当前不产生可观测的锁竞争（取锁走写锁，整轮未出现任何取锁超过 13ms 的清理链）。
