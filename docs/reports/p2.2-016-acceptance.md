## 一、结论

1. **G-1（边界压力用例）成立**：`stress.boundary` 的 `L0` / `N` 每次由标定得出（本轮 `L0` 55.6 ~ 59.9ms、`N` 51 ~ 54），② 全部 `run_completed` 且 `timeouts == 0`，③（`2N`）稳定出现 44 ~ 52 条「执行排队超时」；单跑连续 3 次全绿，`--all` 中 5 次全绿 + 1 次无关用例抖动。
2. **G-2（`server --async`）成立**：`-a` / `--async` 可解析、派生即返回、子进程常驻、失败路径一行原因；前台路径零变化（Batch D 已验收，本轮由 `cli.async_server` 与 `--help` 复核）。
3. **G-3（测试数据通道收敛）成立**：`crates/bin-tests` 不再读取 `server.log`；服务端数据只经 `GET api/probe/metrics` 取得（同一个 `MetricsSnapshot` 类型）；`metrics` 模块内采集型阈值日志为零；原四处日志断言的等价替换在报告里逐条可见。
4. **G-4（纪律入库）成立**：`AGENTS.md` 新增「### 测试数据采集」六条，逐条对应已落地实现，无「暂不适用 / 待实现」例外。

**本轮改动的两处口径**（详见 §八）：KI-P2.2-002 按 D-P2.2-016 结案（内边界总耗时上界加收尾余量，`N` 与公式不动）；新增 KI-P2.2-003（`chat.multiturn` 的 Mock 观测偶发 404，与本阶段改动无关）。
