# P2.1-008.1 同步锁与共享状态复核（锁面审查）

- **阶段**：P2.1（Batch B）
- **任务**：P2.1-008.1
- **前置**：[`p2.1-008-limit-and-journal.md`](p2.1-008-limit-and-journal.md)
- **结论**：进程内共 12 处同步原语，**只有 `RuntimeState.inner`（整表 `RwLock`）落在每帧事件路径上**；其余都在会话级、请求级或启动期触发。互斥原语（会话锁、客户端串行锁、TUI 连接状态机）提供的是「串行语义」，不适用 `ArcSwap`。本任务**未改任何锁实现**，同时补齐了「整表锁等待 / 下行转发临界区 / 会话锁取锁等待」三组观测口径；授权后两轮实测（`runtime tui` 32/32、`--all` 73/73）读到的读写等待与单帧转发耗时全部为 **0ms**，100ms 阈值零触发 → **逐项结论「不改」，本任务结案**。

补充事实（决定上表的量级判断）：

- #1 的写锁来源不止转发：`heartbeat` / `inquire` / `mark_stream_closed` / `open_stream` / `occupy` / `release` / `insert_session` / `take_session` / `take_marks` 都是写锁。其中**只有 `Downlink::forward` 是每帧一次**，其余是会话级或请求级。
- #1 的读锁来源是 `client` / `clients` / `occupancy_of_*` / `producer` / `notify_run` / `occupied_sessions` 等，全部在锁内只做 clone 后立即放锁（`README` 第五节规则）。
- `read` / `write` 的取锁封装只有两处（`registry.rs` 底部的两个 helper），因此观测点集中，不需要铺开插桩。
- 写者的 `append` 是「一个会话一个写者任务」，锁的争用者只有同一会话内的写者与停止路径的 `flush`。

## 二、分类与逐项结论

按「这把锁在提供什么」分类，避免把语义问题当性能问题：

| 类别 | 成员 | `ArcSwap` 是否适用 | 结论与理由 |
|---|---|---|---|
| **互斥原语** | #2 会话锁、#4 客户端串行锁、#8 TUI 连接状态机 | **不适用** | 它们提供的正是「同一会话 / 同一客户端同一时刻只有一个动作」的语义，换成无锁反而要自己实现互斥。P2.1-005 / 007 已经把「全局一把」收窄为「按客户端 / 按会话一把」，剩下的是必要串行 |
| **读多写少快照** | #7 `LinkSnapshot` | 技术上适用 | 但读侧只有 `shutdown` 与 `lib-bin-tui::testing`，不在 UI 刷新路径上（UI 走 `updates` 通道）。改造只能带来「少一次互斥」，无可观测收益 → **不改** |
| **整表状态** | #1 `Registry` | 适用，但有前置 | 写侧 ArcSwap 要整表 clone（`clients` + 两个占用索引 + `marks` + `channels` + `sessions` 六个 map）；直接换等于把写锁换成 clone 成本。**必须先拆掉每帧写锁**（见 §五），再判断是否还值得 |
| **阻塞线程内短锁** | #5 写者 `journal` | 不适用 | 锁只覆盖一次 `append` / `flush`，跨不过 `await`，且 P2.1-008 已测「100 帧单帧最长 0ms、50ms 阈值零触发」。要减的是「单写者 + 频道」的结构，不是锁类型 |
| **小表短锁** | #3 `Finalizer`、#6 `RunCancels`、#4 的锁表 | 技术上适用，不划算 | 条目数上界由「在途收尾数」「全局许可数」「并发客户端数」限定，#6 的整表 clone 成本随在跑 Run 数线性增长，与锁内几次 map 操作相比没有优势 → 不改 |
| **启动期一次性** | #9 `OnceLock` | 不适用 | 只写一次，读是普通原子读，本来就没有排队 |

结论一句话：**本轮没有「确定该改」的项**；#1 是唯一可能值得改的项，已通过观测口径变成可判定，判定需要一轮授权跑。

## 三、本次新增的观测口径

只在 `metrics` 特性下采集（D-P2.1-008），正式构建仍是空实现、不新增静态内存。

`crates/manager-agent/src/runtime/metrics.rs`：

| 新增 | 内容 |
|---|---|
| `RegistryLockMetrics` | 读锁 / 写锁各计「次数、累计等待、单次最长等待」，另有「下行转发次数」与「单帧转发临界区最长耗时」 |
| `SessionLockWait` | 会话锁**取锁等待**（只算等锁，不含锁内持有；持有时间沿用 P2.1-006 的 `SessionLockHold`） |
| `record_registry_read` / `record_registry_write` | 由 `registry.rs` 的 `read` / `write` 两个 helper 调用 |
| `record_downlink_forward` | 由 `Downlink::forward` 调用，覆盖「取写锁 → 序号自增 → 投递」整段 |
| `record_session_lock_wait` | 由 `RuntimeState::lock_session` 在 `lock_owned().await` 前后调用 |
| 阈值 | 等待 / 转发临界区超过 100ms 记 `warn`（`LOCK_WAIT_WARN_MS`），日志级别与 P2.1-003 一致 |

`crates/bin-tests/src/observability.rs`：测试报告「运行时指标」一节新增三行（取会话锁等待、注册表整表锁、下行转发），不需要额外命令。

读法：

- 「写锁次数」应当约等于「下行转发次数 + 会话级写操作次数」；两者之差说明写锁被非事件路径占用。
- 「写锁最长等待」是判断「整表锁是否在制造排队」的直接证据；结合「单帧转发最长耗时」（临界区本身多长）可以区分「临界区长」与「争用重」。
- 「取会话锁等待」与已有的「会话锁持有」区分开：前者是排队，后者是临界区，P2.1-006 只解决了后者。

## 四、实测数据与结论

授权后跑两轮（默认并发，`metrics` 特性打开）：

| 观测 | `runtime tui`（32/32，墙钟 18s） | `--all`（73/73，墙钟 33s） |
|---|---|---|
| 注册表整表锁 读 | 131 次，最长等 **0ms** | 138 次，最长等 **0ms** |
| 注册表整表锁 写 | 296 次，最长等 **0ms** | 307 次，最长等 **0ms** |
| 下行转发 | 99 帧，单帧最长 **0ms** | 100 帧，单帧最长 **0ms** |
| 取会话锁等待 | 20 次，最长 **0ms**（累计 0ms） | 22 次，最长 **0ms**（累计 0ms） |
| 会话锁持有（对照） | 20 次，最长 1ms（累计 10ms） | 22 次，最长 1ms（累计 11ms） |
| 事件落盘（对照） | 99 帧，单帧最长 0ms | 100 帧，单帧最长 1ms |
| 100ms 阈值 `warn` | 零触发 | 零触发 |

数据来源与边界：

- 数值取自测试报告的「运行时指标」一节，即**测试进程内装配**的那份运行时（`support::installed` / `runtime_state`）。共享 / 隔离用例的服务端是子进程，其计数不可导出，只能看阈值行：两轮的 `server.log` 里没有一条「注册表读锁等待时间过长」「注册表写锁等待时间过长」「下行转发的临界区耗时过长」「会话锁取锁等待时间过长」，即子进程侧同样零触发。
- 「写锁次数」296 / 307 明显大于「下行转发」99 / 100：差额来自 `heartbeat` / `inquire` / `open_stream` / `occupy` / `release` / `take_marks` 等会话级写操作（心跳扫描 5s 一轮），与 §一 的「只有 `forward` 是每帧一次」一致。
- 这三组指标是本任务新增的，因此本表是**首轮基线**，不是「修复前 / 修复后」对照。

逐条判定：

| 判据 | 数据 | 结论 |
|---|---|---|
| 整表锁是否在制造排队 | 读 / 写最长等待均为 0ms，`LOCK_WAIT_WARN_MS` 零触发 | **不改**：`RwLock<Registry>` 在当前负载下没有可观测争用 |
| 单帧转发临界区是否变长 | 单帧最长 0ms，与 journal 单帧同阶 | **不改**：临界区只是序号自增 + 一次 `try_send` |
| 会话锁排队是否存在 | 取锁等待 20 / 22 次全为 0ms | **不改**：排队只可能出现在「刚释放就重新占用」，本轮未出现 |
| 串行语义未被破坏 | 32/32、73/73 全绿（含 `runtime.occupancy` / `runtime.handler` / `runtime.disconnect` / `tui.reconnect`） | 通过 |

因此本任务以「**全部不改**」结案：§五 的候选改造**不实施**，只作为「若将来出现毫秒级等待」的处置路线保留；判据里「若引入 `ArcSwap`」一条条件未触发。

结论只覆盖当前负载形态（18 条并发用例、共享服务端、`max_concurrent_runs = 4`）。若将来出现「单进程多客户端高频事件流」，或按核数放大许可（P2.1-015）后写锁次数显著上升，需要重跑这两轮并复读本表。

## 五、候选改造路线（本轮不实施）

本轮数据不支持改造，因此下列步骤**不实施**；只有将来出现毫秒级等待（或 §四 末尾列出的负载变化）时才按顺序执行，且**一次只改一处**：

1. **先拆每帧写锁**（结构改动，不动语义）：把 `channels` 与「客户端状态 + 序号」从整表锁里拆出来
   - `channels: ArcSwap<HashMap<String, Arc<ClientChannel>>>`：开流 / 关流时整表 clone 后 `store`，转发时 `load` 后 `Arc::clone`，不再取整表写锁；
   - 序号生成改 `AtomicU64`，随 `ClientChannel` 一起持有；`forward` 只读客户端状态快照。
   - 保留 `stream_generation` 的判定语义：`mark_stream_closed` 仍按「登记的那条通道是否还是当前世代」判断，只把「比对 + 移除」从整表写锁挪到通道表的写路径。
2. **再评估整表 ArcSwap**：只有第 1 步之后写锁次数仍高时才做；此时写侧 clone 的是「客户端 / 占用 / 会话」三类表，成本与「一次占用或释放」同阶（会话级，不是帧级）。
3. **不动互斥原语**：会话锁、客户端串行锁、TUI 连接状态机保持现状；测试侧串行夹具保持现状。

风险点（改造时必须逐条核对）：`forward` 与 `open_stream` / `mark_stream_closed` 的先后语义；`take_marks` 与处理链入口的合并通知语义；事件「先落盘 flush 再转发」的顺序；`README` 第五节的「不持锁跨 `await`」。
