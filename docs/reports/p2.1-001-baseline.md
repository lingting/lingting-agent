## 一、结论

**K-1 在当前代码上未复现。** 默认并发（18）连续 3 次 `--all` 全部通过，失败数为 0；低并发对照与本文档涉及的单领域选择器同样全绿。因此：

1. P2.1-001 的「失败集合逐次变化」这一判据**无法用当前代码复现**，只能以「未复现」记录。
2. 失败耗时是否压在用例内部上限（`STREAM_TIMEOUT = 20s`、`RECONNECT_TIMEOUT = 25s`、`flow::RUN_TIMEOUT = 30s`、`runner::CASE_TIMEOUT = 60s`）**无失败样本可判**；只能给出「无失败 → 无压线」的空结论。
3. K-1 记录的失败画像（57 条用例、2 条失败、`session.message` 44.5s）与本次观测（73 条用例、0 条失败、`session.message` 221ms）差距过大，**不能仅归因为「运气好」**，见第四节。

| 运行 | 并发度 | 用例数 | 通过 | 失败 | 墙钟耗时 | 用例耗时之和 |

- **并发 4 与并发 18 的墙钟耗时相同**（33.9s vs 34.0s）。这直接否证「并发度高导致排队」这一解释路径：把并发压到 4 并不能让全量变快，说明当前不存在因共享服务端排队而拖出来的额外时间。

## 四、与 K-1 记录的差异

| 项 | K-1 记录（P2 Batch E，2026-11-21） | 本次观测 |
|---|---|---|
| 用例总数 | 57 | 73（P2 验收提交补齐了 `llm.canary` / `persist.*` / `run.*` 等 16 条） |
| 默认并发 `--all` | 2 条失败（集合逐次变化） | 0 条失败（3 次一致） |
| `session.message` | 44.5s 失败 / 2.7s @ 并发 4 | 221ms |
| `tui.reconnect` | 20.0s 失败 / 15.1s 单跑 | 15.1s 通过 |
| `--concurrency 4` | 57 条全过 | 73 条全过 |

差异的可能来源（**本轮未定性，不得据此结案**）：

1. **用例集合已变**：K-1 记录在 57 条用例的时代，`874c43b`（P2 端到端验收）之后才补齐到 73 条。共享分片里新增的用例改变了调度构成，可能把原来挤在一起的长耗时用例错开。
2. **机器负载不同**：K-1 是在 P2 验收当天（同时跑过 `make release` 全量构建、`pnpm`、Playwright）的记录，本次是空闲机器。`tui.reconnect` 这类「等心跳扫描」的用例对系统负载最敏感。
3. **`session.message` 的 44.5s 无法用现有常量解释**：它既不是 `STREAM_TIMEOUT`（20s）也不是 `RUN_TIMEOUT`（30s），更像「30s + 10s 两段等待叠加」的结果，说明当时的失败可能与「下行流迟迟不结束」而不是单纯调度有关。该路径在当前代码上完全走不到，**不能排除 K-1 记录中的失败另有未记录的条件**。

结论：**K-1 的根因分析（H-1 ~ H-4）在当前代码上既未被证实也未被证伪**——它首先需要一次可复现的失败，而本轮拿不到。

## 五、对后续任务的影响

1. **P2.1-002 / 003 照常推进**：阻塞点审计与服务端可观测性不依赖「是否复现」，且它们是判据 G-1-3（关闭判定有数据支撑）与 D-P2.1-004（全绿 + 指标达标）的前置。
2. **Batch B 的路径需要重排**：README §5.1 的「量测 → 修阻塞 → 解串行 → 复核」以「有一批可归因的失败」为前提。当前前提不成立，H-1 ~ H-4 只能靠**结构性证据**（同步阻塞点确实存在、断连链确实是全局互斥）与**指标基线**推进，无法靠「改完失败数下降」证明收益。
3. **`tui.reconnect` 是唯一贴近上限的用例**（15.1s / 20s `STREAM_TIMEOUT`）。若 K-1 的原始失败形态是「等心跳 → 重连 → 重载」这条链被系统负载拉长，那么它是当前代码上最可能复现的入口；后续若要复现，应优先加压这一条，而不是压全量并发。
4. **本阶段不得用「默认并发全绿」直接结案**（D-P2.1-004 ②）：三次全绿只是必要条件，仍需给出指标侧的「为什么以前会超时」。

## 六、加压复现实验（Batch A 追加）

目的：排除「默认并发全绿只是机器空闲」这一解释。用背景 CPU 忙循环制造可控压力（不用任何测试侧限流或代码改动），观察失败是否出现、耗时上限被谁先撞到。

| 实验 | 背景负载 | 运行 | 并发度 | 结果 | 墙钟耗时 |
|---|---|---|---|---|---|
| L-1 | 6 个忙循环（约 33% CPU） | `--all` | 18 | 73/73 通过 | 34.0s |
| L-2 | 18 个忙循环（核心饱和） | `--all` | 18 | 73/73 通过 | 37.1s |
| L-3 | 18 个忙循环（核心饱和） | `tui --concurrency 14`（14 条 TUI 用例同时跑） | 14 | 14/14 通过 | 17.3s |
| L-4 | 36 个忙循环（2× 超订） | `--all` | 18 | 73/73 通过 | 74.2s |
| L-5 | 4 路顺序大文件写（磁盘写入压力） | `--all` | 18 | 73/73 通过 | 34.1s |

### 各档负载下最接近上限的用例

| 实验 | 最长用例 | 耗时 | 对应上限 |
|---|---|---|---|
| L-2 | `client.errors` | 35.3s | `runner::CASE_TIMEOUT` 60s |
| L-2 | `web.e2e` | 22.3s | `runner::CASE_TIMEOUT` 60s |
| L-3 | `tui.reconnect` | 15.2s | `STREAM_TIMEOUT` 20s |
| L-4 | `web.e2e` | **50.4s** | `runner::CASE_TIMEOUT` 60s |

### 结论

1. **CPU 压力只拉长耗时，不产生失败**：墙钟从 34.0s → 37.1s → 74.2s（2× 超订下翻倍），失败数始终为 0。
2. **CPU 抢占不是 K-1 的触发条件**。K-1 的失败形态是「耗时恰好压在用例内部等待上限」（20s / 44.5s），属于**等待型超时**；这类超时在 CPU 被抢占时应当表现为耗时普遍变长而不是精确压线。加压实验没有复现这个特征。
3. **当前真正贴近上限的是子进程型用例，不是共享服务端的长耗时用例**：L-4 里 `web.e2e` 到 50.4s（Playwright 起浏览器，与共享服务端无关），`client.errors` 稳定在 33s 上下。而 K-1 点名的 `session.message` 现在是 221ms、离上限有两个数量级。这条反差说明 K-1 的画像（共享分片的长耗时用例被饿）与当前代码的耗时结构已经对不上。
4. **因此 K-1 的成因不排除是当天环境因素**（P2 验收当天同时跑过 `make release` 全量构建、`pnpm` 与 Playwright，另有杀软对临时目录的扫描）。这一点无法在事后用代码复现，只能记为「未定性」。

### 仍未排除的可能性

- **服务端侧阻塞**（SQLite 单写者、WAL checkpoint、事件逐帧 flush）：L-5 用 4 路顺序大文件写压了磁盘，耗时几乎不受影响（34.1s，仅 `web.ui` 从 6.9s 涨到 8.3s），同样没有复现。要复现大概需要更强的同步写放大（例如同时跑 `make release` 的链接阶段），本轮未做。
- **测试进程内 worker 被同步等待吃光**：需要**全部** worker 同时阻塞才会让定时器停摆。当前 `--all` 的首批 18 条用例里同步阻塞的点不够多（见 P2.1-002 的审计），所以只在理论上成立，实际撞不到。
- 上述两项都需要 P2.1-002 / 003 的指标才能定性，而不是继续加压。
