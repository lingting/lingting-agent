# P2.1-008.2 数据库读路径复核（表级内存快照 + 失效事件）

- **阶段**：P2.1（Batch B）
- **任务**：P2.1-008.2
- **前置**：[`p2.1-008-limit-and-journal.md`](p2.1-008-limit-and-journal.md)、[`p2.1-008.1-lock-audit.md`](p2.1-008.1-lock-audit.md)
- **结论**：执行期共 10 类数据库访问，**全部落在 API 请求上，每次请求 1~2 条语句；事件转发、心跳扫描、断连标记、事件落盘这些高频路径根本不碰数据库**。当前没有任何轮询型调用方（前端只有 chat 页，TUI 按需调用，`probe/health` 只在连接 / 重连各一次），因此「表级内存快照」缺少收益前提 → **逐项「不改」结案**。机制口径已定稿（失效式，不是预取式），触发条件写在 §七。

## 一、执行期读清单

「语句数」按一次调用会发出的 SQL 条数计；`×` 表示与数据库无关。

| # | 调用点 | 语句数 | SQL 形状 | 频率（谁调） | 结果是否作权威判定 | 结论 |
|---|---|---|---|---|---|---|
| 1 | `api/probe/health` → `running_run_count()` | 1 | `SELECT COUNT(*) FROM runs WHERE status = 'RUNNING'`（走 `idx_runs_status`） | 客户端连接 / 重连各一次 | 否（仅展示） | 不改（索引聚合） |
| 2 | `api/session/list` → `sessions()` | 1 | 全表 + 每行 `(SELECT COUNT(*) FROM messages WHERE m.session_id = s.id)` 相关子查询 | 按需（TUI 命令；前端暂无会话列表页） | 否（展示） | 不改（无轮询调用方） |
| 3 | `api/message/list` → `require_session()` + `messages()` | 2 | 带 `COUNT(*)` 子查询的会话投影 + `SELECT messages … ORDER BY seq` | 按需 | 存在性必须实时 | 不改（存在性那一条可省，见 §七） |
| 4 | `api/message/create` → `require_session()` + 事务 | 1 读 + 1 事务（3 条写） | 同上 + `INSERT messages` / `INSERT runs` / `UPDATE sessions` | 每发一条消息 | **是**（会话存在 + 模型归属） | 不改 |
| 5 | `api/run/get` → `run()` | 1 | `SELECT … FROM runs WHERE id = ?` | 按需 | **是** | 不改 |
| 6 | `api/run/cancel` → `require_run()` + 条件 `UPDATE`（失败再读一次） | 1~3 | `SELECT` + `UPDATE … WHERE id = ? AND status IN (…)` | 每次取消 | **是**（条件更新，D-P2-030） | 不改（不得缓存） |
| 7 | Run 执行期（每个 Run 一次） | 5~6 | `next_queued_run` / `user_prompt` / `start_run` / `session_summary` / `history_before_run` / `complete_run`（事务） | 每 Run 一次 | **是** | 不改（一次写一次读） |
| 8 | 会话停止 / 释放占用 → `cancel_session_runs()` | 1 | `UPDATE runs SET status = … WHERE session_id = ? AND status IN (…)` | 每会话一次 | **是**（终态权威） | 不改（写） |
| 9 | 占用建立 → `has_session()` | 1 | `SELECT 1 FROM sessions WHERE id = ?` | 每次占用 | **是** | 不改 |
| 10 | 心跳扫描 / 断连标记 / 事件落盘 / 下行转发 / SSE 帧 | × | — | 每 5s / 每次更新 / 每帧 | — | 与数据库无关（状态在内存 + 事件文件） |

关键读数：

- **真正的高频路径一条 SQL 都没有**：#10 覆盖「每帧事件落盘 + 转发」「心跳扫描」「断连清理」，`RuntimeState` 与 journal 都在内存 / 文件里；P2.1-003 的「取数据库连接」在整轮全量里只有 3 次，量级一致。
- 最重的单条语句是 #2 的相关子查询（会话数 × 每会话消息数），其次是 #3 为「判断会话存在」付出的一次带 `COUNT(*)` 的投影。
- 只读展示型只有 #1 与 #2 两条；其余 6 条都参与状态判定，**按本任务口径一律不缓存**。

## 三、分类与判定

| 类别 | 成员 | 快照化 | 判定 |
|---|---|---|---|
| **权威判定型** | #4 会话存在 + 模型、#5 Run、#6 取消条件更新、#7 执行期、#8 终态写入、#9 占用校验 | **禁止** | 缓存会破坏 D-P2-029 / D-P2-030 的条件更新与取消语义：读到旧状态就会写出错误的终态 |
| **只读展示型** | #1 探活计数、#2 会话列表 | 技术上可行 | 无轮询调用方、单条语句本身就是索引聚合 / 单表扫描级 → **不改** |
| **一次写一次读** | #3 用户消息正文、#7 历史消息 | 不划算 | 每次 Run 只读一次，缓存生命周期比读取次数长 |

结论：**没有一条读路径同时满足「高频」「可陈旧」「非权威」三个条件**，因此本任务不引入快照，也不引入 `arc-swap`。

## 五、机制口径（定稿，本轮不落地）

启用时按下列形态实现，任何偏离都需要在 `decisions.md` 重新登记：

| 项 | 口径 |
|---|---|
| 形态 | **失效式**：写事务提交后发通知 → 快照打脏 / 清空 → 下一次读回源 DB 并替换。**不是**「消费者预取重读」（见 §六） |
| 快照归属 | `service-core`（`repository` 只允许被本 crate 的 Service 调用，`AGENTS.md` 第 7 条）；`manager-agent` 只负责订阅并调用 `refresh_*` / `invalidate_*` |
| 通知类型 | `types-core`（只放空结构体类型，不倒置依赖方向）；走 `framework-bus` 的纯通知语义：不带数据、边沿触发、可合并 |
| 启动顺序 | 先 `watch` 再全量加载，避免「加载完到订阅之间」丢通知 |
| 读路径 | `ArcSwap::load_full()` + `Arc::clone`，不在锁内做业务；无锁读 |
| 单飞 | 同一张表同一时刻最多一个回源任务，其余等待同一个结果，避免惊群 |
| 有界陈旧 | ≤ 1 个通知往返；回源失败保留旧快照 + `warn`，等下一次通知重试 |
| 可观测 | 命中 / 回源次数、刷新耗时、最近一次刷新时刻，全部在 `metrics` 特性下（D-P2.1-008） |
| 禁止 | 权威判定读（#4~#9）缓存；缓存放 `lib-db` 或 `types-core`；用缓存值参与取消 / 终态判定 |

## 六、被否决的变体

| 变体 | 为什么否决 |
|---|---|
| 预取式：写后由消费者重读 DB 并替换快照 | 没有读放大时，它把「每次读一条查询」变成「每次写一次查询」，写路径反而更贵；而且写完立刻读回来，与「读时回源」等价，只多了常驻的消费者任务与生命周期管理 |
| 权威判定读也走快照 | 破坏条件更新的正确性（D-P2-030）：取消与终态写入必须看到数据库的当前状态 |
| 把快照放 `lib-db` | `lib-db` 只承载连接、事务与迁移，不承载业务语义；放进去会让所有使用方都被动继承一张业务表 |
| 把快照放 `types-core` | 类型 crate 不持有运行时状态，且会让数据访问跨 crate 边界 |
| 为「设置」类读提前实现 | 当前没有配置 / 设置表：`config.toml` 由 `lib-bin-cli` 装载后经 `ProviderService` 常驻内存，不存在重复查询。按「不写投机性代码」的原则不预实现 |

## 七、触发条件与遗留候选

**启用快照的触发条件**（满足任一条就可以启动实现，并且先用 `metrics` 计数证明）：

1. 出现轮询型调用方（例如前端定时刷新会话列表、健康检查被高频率拉取）；
2. 某个只读 API 的读频次在指标里显著高于写频次，且单次语句耗时进入毫秒级；
3. 会话 / 消息规模增长到 `session/list` 的相关子查询成为可观测成本（届时更应先考虑 §七 的两条 SQL 改造，而不是引入缓存）。

**遗留候选（属于 SQL 读放大，不在本任务范围，需单独授权）**：

| 候选 | 现状 | 改法 | 收益 |
|---|---|---|---|
| `message/list` 的存在性检查 | `require_session()` 使用带 `COUNT(*)` 子查询的会话投影，只为判断存在 | 改用已有的 `has_session()`（`SELECT 1`） | 每次列消息少一次相关子查询 |
| `sessions()` 的消息数统计 | 每行一条相关子查询 | 改 `LEFT JOIN` + `GROUP BY` 一次聚合成表 | 单表扫描一次，而不是 N 次索引扫描 |

两条都不涉及缓存与事件，语义不变；但会改动 `repository` 的 SQL，属于「额外新增处理」，因此按仓库约定先停在这里等确认。
