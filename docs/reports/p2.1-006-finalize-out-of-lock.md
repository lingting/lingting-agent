# P2.1-006 收尾等待移出会话锁（H-2）

- **阶段**：P2.1（Batch B）
- **任务**：P2.1-006
- **前置**：[`p2.1-005-chain-parallel.md`](p2.1-005-chain-parallel.md)
- **结论**：会话锁内只剩状态切换，收尾（写库取消 → 执行队列收尾 → 写者 flush）交给后台任务。**会话锁持有时间与收尾时长解耦**：全量跑下来 22 次取锁、最长 1ms、累计 14ms，而同一轮里单次会话停止最长 16~22ms。关闭流程仍是唯一「等全部收尾完成」的路径。

---

## 一、改动

| 位置 | 改动 |
|---|---|
| `runtime/registry.rs` | 新增 `Finalizer`：每个会话一把「在途闸门」（`Arc<tokio::sync::Mutex<()>>`，登记时先占住、任务结束时先摘登记再放行）；新增 `lock_session`（返回带计时的 `SessionLock` 守卫）、`await_previous_stop`、`has_pending_stop`、`drain_finalizations`、`stop_session_in_background`（摘下会话 + 起后台任务 + 10s 超时兜底 + `warn`） |
| `runtime/occupancy.rs` | `release_occupancy`：锁内只做「摘下运行时会话 + 撤回占用登记」，不再 `await stop` |
| `runtime/handler.rs` | `clean`：锁内只做「摘下运行时会话」，不再等收尾；`shutdown` 在结束前 `drain_finalizations()`，保持「关闭必须等全部收尾」 |
| `runtime/occupancy.rs` | `acquire`：建立之前先等同一会话上一次的后台收尾（闸门 + 重试），保证同一会话不并存两份运行时会话 |
| `runtime/metrics.rs` | 新增「会话锁持有」指标（次数 / 累计 / 最长，≥200ms 打 `warn`），由 `SessionLock` 的 `Drop` 记账 |
| `runtime/session.rs` | 删除不再使用的 `stop_session`（等待版）；`RuntimeSession::stop` 本身不动 |

保持不变：`RuntimeSession::stop` 的四阶段与写序（先落盘 flush 再转发）、终态事件语义、`shutdown` 的 `server_shutdown` 覆盖规则、同一会话串行。

## 二、修复前后对照（默认并发 18，73 个用例）

| 观测 | 修复前 | 修复后 |
|---|---|---|
| 会话锁持有 | 无此指标；锁内包含 `stop()` 全程（写库取消 + 执行队列收尾 + 写者 flush） | **22 次，最长 1ms，累计 14ms** |
| 单个客户端清理链 | 最长 15~19ms（含锁内停止会话与 flush） | **最长 0ms**（锁内不再有等待） |
| 会话停止（后台任务） | 11 次，最长 12~19ms | 11 次，最长 16~22ms（与锁无关，边界不变） |
| `runtime.journal` 的终态事件 | 释放返回时已 flush | 释放返回后异步落盘，用例改为等它出现 |
| 结果 | 73/73 | 73/73 |

读法：

- 修复前「清理链最长 15~19ms」是**锁内**耗时；修复后链最长 0ms，说明锁里只剩内存记账，收尾已经移到锁外。
- 会话停止的耗时没有变（20ms 量级），但它是后台任务的耗时，不再计入任何临界区。
- 锁持有最长 1ms：即使后台收尾跑到 10s 超时上限，锁也不会被拖住。

## 三、语义变化与用例调整

**唯一的对外可观察变化**：`api/occupancy/delete` 与断连清理返回时，运行时会话的终态事件可能还没落盘（此前是「返回即已 flush」）。`shutdown` 例外——它等全部收尾完成。

因此 `crates/bin-tests/src/cases/journal.rs` 的两处断言改为先等终态事件出现再断言：

| 断言 | 调整 |
|---|---|
| 释放占用后追加一条 `run_cancelled`（seq = 3，原因文本固定） | 增加「等文件到 4 行」，内容与 seq 断言不变 |
| 慢客户端释放后只追加一条终态事件（`total + 1` 行） | 增加「等文件到 `total + 1` 行」，条数与 seq 连续性断言不变 |

同时 `acquire` 侧补了闸门等待：同一会话「刚释放就重新占用」时会等上一次收尾完成。这条路径不影响其它会话的占用与释放——闸门是会话级的，不新建全局串行点。

## 五、注意点

1. **收尾是「尽力而为」**：后台任务有 10s 上限（执行队列自带 5s），超时打 `warn` 并放弃等待；事件文件可能因此少一条终态事件，但不会阻塞占用 / 释放。
2. **关闭流程是唯一等等待点**：`shutdown` 先跑链、再停残留会话、最后 `drain_finalizations`，保证关闭后不留未收尾的事件文件。
3. **锁持有指标会被防御路径放大**：`start_session` 里「同一会话存在未停止的运行时会话」的防御分支仍在锁内 `await stop`（不应发生），一旦触发会在这条指标上显形。
