## 三、首轮红灯的定位

**现象**：`runtime.disconnect`（shared，81ms）报「客户端主动断开：应有一条终态事件，实际 1 条」。

**证据链**：

| 证据 | 结论 |
|---|---|
| 该轮事件文件（`lingting-agent-tests/units/assembly-1795405722705/events/`）事后全是 2 行，5 条夹具都带 `run_cancelled` 且 `error` 为固定文本「客户端连接已断开」 | 终态事件**最终写出来了**，不是丢失 |
| 5 条夹具的 `run_cancelled` 时间为起手事件之后 15ms / 27ms / 28ms / 45ms / 64ms | 落在用例读取之后，是毫秒级窗口 |
| 修复前第 2 / 3 轮的同一用例分别 110ms / 108ms 通过 | 窗口窄，三轮里只撞到一次 |
| 代码对照：`runtime/handler.rs::clean` 锁内只 `stop_session_in_background`，收尾（写库取消 → 执行队列收尾 → 写者 flush）在后台任务；`cases/journal.rs` 在 P2.1-006 已改为「先等事件出现」，`cases/disconnect.rs` 未改 | 用例假设了「清理链返回时终态事件已 flush」，与 P2.1-006 的语义变化不符 |

**判定**：产品侧语义符合 P2.1-006 的既定口径（`docs/reports/p2.1-006-finalize-out-of-lock.md` 第三节：断连清理返回时终态事件可能还没落盘，`shutdown` 例外）；缺口在用例侧。已登记为 `.steps/p2.1/known-issues.md` 的 K-3，处置口径见 `.steps/p2.1/decisions.md` D-P2.1-014。

## 八、注意点

1. **K-1 的最终口径**（未复现 + 环境因素未排除 + 五档加压结果）在 P2.1-014 的验收报告里定稿；本轮只提供「默认并发三轮全绿」这一条回归证据，不主张修复收益。
2. **窗口型失败不会因为「跑绿了」而消失**：`runtime.disconnect` 的缺口一旦回退（例如把等待删掉），在毫秒级窗口上仍会偶发复现。K-3 的验收口径因此固定为「断言前必须有等待」，而不是「三轮都绿」。
3. **`client.errors` 占 32.8s，是墙钟的近似下限**：它单独一条就超过全量墙钟 33s 的临界，任何一轮里它的抖动都会直接反映到墙钟上。
4. **`下行通道丢弃 1 次/轮` 未变**：这是 `web.shutdown` / 断连用例里已被 P2.1-003 记录的正常路径（判流废），不是新增丢弃。
5. **本轮未改产品代码**：唯一改动是用例等待。产品侧语义（终态事件异步落盘）沿用 P2.1-006 的口径，未回退。
