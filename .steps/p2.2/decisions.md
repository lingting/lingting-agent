## D-P2.2-001 子进程指标出口：debug + `metrics` 限定的探针

- **状态**：`DECIDED`
- **问题**：服务端是子进程，`bin-tests` 要拿它的运行时指标，通道放在哪？
- **背景与证据**：
  - 现在的指标采集都在服务端进程内（`manager-agent` / `agent-runtime` / `lib-db` 的原子累加），测试进程只能看到 `metrics` 特性下的阈值日志（README §三 C-4）。
  - `bin-tests` 的 `Server::stop` 用 `child.start_kill()`（`crates/bin-tests/src/util/server.rs`），不触发优雅关闭，所以「退出时写文件」在现有收尾路径上拿不到数据。
  - `lib-web` 已有 debug-only 探针先例：`api/probe/shutdown`（`#[cfg(debug_assertions)]`）。
- **可选方案**：
  1. `GET api/probe/metrics`，`#[cfg(all(debug_assertions, feature = "metrics"))]`，返回聚合快照 JSON；
  2. 服务端优雅关闭时把快照写 `<AGENT_HOME>/metrics.json`，`Server::stop` 改为探测关闭 + 等进程退出；
  3. 周期（如 1s）把快照刷到文件，保留 kill 收尾；
  4. 方案 1 + 方案 2 并存。
- **决策**：①。
- **理由**：
  - ②要求把 70+ 条用例的收尾从 kill 改成优雅关闭，会在全部用例上引入「清理链排空」的额外等待，风险与收益不成比例；且拿到的是**收尾后**的数字，压力用例会被 300 条清理链污染。
  - ③有最多 1s 的延迟，压力用例的窗口只有 3s，误差与窗口同阶；且仍需引入文件格式与路径约定。
  - ④的收益（进程崩溃后仍有一份数据）不足以抵消两套机制与两套口径的维护成本。
  - ①的代价（新增一条探针接口）被三个条件压住：只在 `debug_assertions`、只在 `metrics` 特性、`make gen` 不启用该特性因此不进 SDK。它与既有 `api/probe/shutdown` 同规格，不进入 release。
- **约束**：
  - 接口只在 `metrics` 构建注册；release 与普通 `make build` 不出现该路径（G-3-7 可核）。
  - 返回的 DTO 必须是 `manager-agent` 的 `Snapshot` 类型本身，`bin-tests` 反序列化同一个类型，不得复制一份字段（`AGENTS.md` 第 19~22 条）。
  - 缺失快照必须显式「未采集」，用例不得静默跳过断言。
- **承接任务**：P2.2-002、P2.2-005、P2.2-006。

## D-P2.2-002 为审计层给框架 `LoggingConfig` 增加自定义 `layers`

- **状态**：`DECIDED`
- **问题**：`llm.canary` 要断言「`api_key` 没有进日志」。不允许事后扫描日志文本，那这个断言还能怎么做？
- **背景与证据**：
  - `framework-core` 的 `LoggingConfig` 目前只有 `filters: Vec<Arc<dyn Filter<Registry>>>`；`Filter` 只能看到 `Metadata`，看不到事件字段，因此无法判断「本次事件的字段里是否包含敏感串」。
  - `logging::init` 内部已经按层组装 subscriber，但调用方无法追加自定义层。
- **可选方案**：
  1. 给 `LoggingConfig` 增加 `layers`（`Box<dyn Layer<Registry> + Send + Sync>`）与 `push_layer`，`lib-core` 在 `metrics` 下挂审计层；
  2. `lib-core` 在 `metrics` 下自己组装 subscriber（复制框架的 console / file / archive 逻辑）；
  3. 放弃「日志泄漏」这条断言，只断言「事件文件 / 数据库 / 接口响应里没有该密钥」；
  4. 保留原样：事后扫描日志文件（与本阶段纪律直接冲突）。
- **决策**：①。
- **理由**：
  - ②是把框架的日志装配复制一份，两份实现必然漂移，代价远大于一个 5 行的配置字段。
  - ③会丢断言力度：密钥最可能的泄漏路径正是日志（错误体、请求体调试日志），删掉它就少了一道真实的防护。
  - ④违反本阶段纪律（G-3）。
  - 框架是本仓库作者自有仓库（`D:/code/lingting/lingting-rust-framework`），P1 已有「为满足需求向框架提交改动」的先例。
- **约束**：
  - 只新增字段与构造函数，不改现有 `filters` / `console` / `directory` / `archive` 的语义与顺序。
  - 审计层只加计数，不改写、不过滤、不落盘，不影响事件内容与去向。
  - 审计层只在 `metrics` 构建编译；正式构建的 `init` 路径等价于现在。
  - 框架改动与主仓库改动的合并顺序必须在阶段报告中写明（跨仓库依赖）。
- **备选（若框架不允许改）**：退回③，并把「日志泄漏不再作为测试断言」写进 `known-issues` 与阶段报告，重新决策。
- **承接任务**：P2.2-003、P2.2-007。

## D-P2.2-003 `stress.boundary` 默认纳入 `--all`

- **状态**：`DECIDED`
- **问题**：一条自带服务端、会开上百客户端、还会故意制造失败的压力用例，要不要进全量？
- **可选方案**：
  1. 纳入 `--all`，与其他用例同批跑（默认并发 54 起）；
  2. 不纳入 `--all`，只能显式 `make test ARGS="stress"` 单跑；
  3. 纳入但由命令行开关控制（例如 `--include-slow`）。
- **决策**：①，同时在报告里记录它对墙钟的增量。
- **理由**：
  - ②等于让它长期不被执行：P2.1 的教训是「没跑到的用例等于不存在」。
  - ③新增一个开关就是新增一条「默认不跑」的理由，最终仍然不跑。
  - ①的风险（与其他用例争抢 CPU / 端口 / SQLite）已经被用例形态压住：它是 `Isolated`，有自己的服务端与自己的 Mock，不碰共享端口 20104；它压的是**它自己的**服务端。
  - 代价是墙钟：三段约 `2 × 3s` 加标定与收尾，与现有最长用例同阶。报告记录增量，超预期再讨论。
- **约束**：用例不得复用共享服务端与共享 Mock；结束时必须让端口与进程可回收。
- **承接任务**：P2.2-009、P2.2-010、P2.2-016。

## D-P2.2-004 `--async` 只写 PID 文件，不提供 `--stop`

- **状态**：`DECIDED`
- **问题**：后台起了服务端，怎么停？要不要顺手做一个 `agent server --stop`？
- **可选方案**：
  1. 只写 `<AGENT_HOME>/server.pid`，停服靠 PID 文件或系统工具；
  2. 增加 `agent server --stop`（读 PID 文件、发信号、等退出）；
  3. 不落 PID 文件，只打印 PID。
- **决策**：①。
- **理由**：
  - 需求只要求「派生新进程常驻、父进程退出」；②是新的运维面（信号语义、跨平台、清 pid 文件、进程不匹配的竞态），超出本阶段目标且会引入新的验收负担。
  - ③让用户拿不到可脚本化的句柄，`cli.async_server` 用例也无法收尾。
  - ①的 PID 文件同时服务于「人工排查」与「用例收尾」，是最小闭环。
- **约束**：
  - PID 文件内容至少含 pid 与服务地址；写入发生在探活成功之后（避免写入一个未就绪的进程）。
  - 不提供自动「启动前先杀旧进程」的行为：重复 `--async` 撞端口时应报错退出，而不是替用户清理。
  - 文档（归 P2.2-015）写明 PID 文件位置与「本阶段无 `--stop`」。
- **承接任务**：P2.2-012、P2.2-013。

## D-P2.2-005 Unix 不为 `setsid` 引入 `libc`

- **状态**：`DECIDED`
- **问题**：Unix 上要做到「父进程退出后子进程不跟着终端走」，通常要 `setsid()`，而 `std` 不提供。
- **可选方案**：
  1. 不引入依赖：`std::process::Command` + stdio 重定向，接受「终端关闭可能收到 SIGHUP」；
  2. 引入 `libc`，在 `pre_exec` 里调用 `setsid()`；
  3. 引入 `nix`（更重的封装）。
- **决策**：①。
- **理由**：
  - 主平台是 Windows 11（`AGENTS.md`），Windows 侧用 `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` 已满足需求；Unix 上「父进程正常退出」本身不会带走子进程，SIGHUP 只在终端会话结束时出现。
  - 引入依赖需要独立决策（AGENTS.md「新增依赖必须考虑职责与依赖方向」）；为了一个尚未被真实场景命中的边界，不值得扩大依赖面。
  - 语义弱在哪里、怎么绕过（`nohup` / 系统服务），写进帮助文案与文档即可。
- **约束**：`--async` 的帮助文案必须写明 Unix 的这条限制；不得在 `.cargo` 配置里隐式引入依赖。
- **承接任务**：P2.2-012、P2.2-015。

## D-P2.2-006 `llm.canary` 改为内存审计，不删除用例

- **状态**：`DECIDED`
- **问题**：`llm.canary` 目前靠检索 `server.log` 与日志目录判定「密钥没进日志」。本阶段禁止日志取数，这条用例怎么办？
- **可选方案**：
  1. 改为「写出侧检测」：审计层在事件构造时比对敏感串并计数，用例断言 `secret_hits == 0`；
  2. 删除该用例（日志泄漏不再作为测试断言）；
  3. 保留原实现，作为「禁止日志取数」的例外。
- **决策**：①。
- **理由**：
  - ②丢掉的是一条真实的安全回归防线（错误体、调试日志都可能带上密钥）。
  - ③会留下与本阶段纪律直接冲突的例外，条款就写不干净（G-4-2）。
  - ①的强度不低于原来：原来在落盘后扫描，现在在**事件构造时**检测，命中即计数，不受日志轮转、归档、级别开关影响；同时 `audit.total > 0` 保留了「日志确实在产出」这一原证据。
- **约束**：
  - `secret_hits` 的比对对象是本次配置里的 `[provider] api_key`，由 `bin-agent` 在日志初始化前取一份传给审计层；不得硬编码示例密钥。
  - 用例失败信息必须点名 `audit.secret_hits`，不得只说「日志含密钥」。
  - 审计层不得把命中的明文写进任何输出（计数即可）。
- **承接任务**：P2.2-003、P2.2-007。

## D-P2.2-007 边界外阶段（`2N`）默认启用

- **状态**：`DECIDED`
- **问题**：压力用例要不要顺带验证「多于边界就会失败」？这会主动制造 `FAILED` Run。
- **可选方案**：
  1. 默认启用 `2N` 阶段，断言「至少一条排队超时」；
  2. 不启用，只做内边界；
  3. 启用但只记录，不断言。
- **决策**：①。
- **理由**：
  - ②只证明「N 个客户端能过」，证明不了「N 是边界」——用例可能只是数字小。
  - ③会在真实回归时留下「超时了但没人管」的空间，等于没有门槛。
  - ①让用例自证门槛位置：`N` 全过、`2N` 必超时，两条一组合，才能说明「卡在不失败的门槛上」这句话成立。
  - `2N` 的失败是**预期内**的：`FAILED` 是服务端的正常终态，不是用例失败；用例断言的是「失败原因是排队超时」。
- **约束**：
  - 断言必须校验失败原因文案（「执行排队超时」，来自 API 的 `RunEvent` / `run/get`），不能只数条数——否则无法区分「边界真实」与「服务端另有缺陷」。
  - 超时的条数与首批超时时刻写入报告。
- **承接任务**：P2.2-009、P2.2-010。

## D-P2.2-009 边界公式口径：`N = floor(T / L0) + 1`，不允许「减一放水」

- **状态**：`DECIDED`
- **问题**：怎么定义「理论上刚好不会失败的客户端数」？
- **背景与证据**：
  - `agent-runtime/src/limit.rs` 的排队超时只覆盖「等全局许可」这一段：`tokio::time::timeout(run_queue_timeout_ms, limit.acquire())`。
  - `max_concurrent_runs = 1` 时，第 `k` 个 Run 的等待约 `(k-1) × L0`（每个 Run 持有许可约 `L0`）。
  - 因此第 `k` 个 Run 超时当且仅当 `(k-1) × L0 > T`，即 `k > T / L0 + 1`。
- **可选方案**：
  1. `N = floor(T / L0) + 1`（不失败的上界），配合 `2N` 外边界；
  2. `N = floor(T / L0)`（保守一格）；
  3. `N = floor(0.8 × T / L0)`（留 20% 余量）。
- **决策**：①。
- **理由**：
  - 用例的语义是「卡在门槛上」；②③都是在门槛下面一段，测不出边界，只是又一条「并发下别崩」的普通用例。
  - ②看似安全，但它与①只差一个客户端，却让「边界」变成「边界附近」，口径变模糊、无法核对公式。
  - 抖动风险由「`L0` 取 3 次最大值」与「报告给出余量」两条控制，不靠偷偷减数。
- **约束**：
  - 公式、推导与 `N` 的取值必须出现在用例注释与报告里；代码中不得出现固化的客户端数量。
  - 若 `L0` 抖动导致连续多次红，只允许两条路：改 `L0` 的取法（更保守的标定），或重新讨论 `T`；**禁止**在公式外加一个「宽容因子」而不写进决策。
  - `N < MIN_CLIENTS`（建议 8）时用例失败并说明「参数不足以形成边界」。
- **承接任务**：P2.2-008、P2.2-009、P2.2-010。

## D-P2.2-010 采集型阈值日志的删除范围

- **状态**：`DECIDED`
- **问题**：「移除当前通过日志获取数据的相关日志」到底删哪些？删多了会丢运维信息，删少了等于没改。
- **背景与证据**：
  - 三处阈值日志：`manager-agent/src/runtime/metrics.rs`（清理链 / 会话停止 / 落盘 / 锁持有 / 锁等待 / 注册表 / 转发）、`agent-runtime/src/metrics.rs`（排队 `debug` / `warn`）、`lib-db/src/observability.rs`（取连接 `debug` / `warn`）。
  - 它们全部在 `metrics` 特性下：正式构建根本不编译，因此**不可能**是生产运维信息，只可能在 `make test` 运行里出现。
  - `handler` / `session` / `journal` / `queue` 里的流程日志（带 `run_id` / `session_id` 的装配、关闭、失败原因）不在 `metrics` 特性下，是真实运维信息。
- **可选方案**：
  1. 删除 `metrics` 特性下所有阈值日志，保留全部非 `metrics` 流程日志；
  2. 只删 `debug` 级，保留 `warn` 级；
  3. 全仓停止使用 `tracing`，只留内存采集。
- **决策**：①。
- **理由**：
  - 阈值日志的存在意义就是「给测试看数字」；数字已经由快照提供，它就是重复通道。
  - ②保留了「测试看日志」的可能，纪律无法收紧到可核。
  - ③过度：日志仍是人工排查手段，本阶段只切断「日志 → 数据」这条路。
- **连带处置**：
  - `lib-db` 在 P2.1-009 下为 `metrics` 特性引入的可选依赖 `tracing` 因此不再需要，随之回退；D-P2.1-009 在本阶段标注为「已回退」，并在阶段报告里注明。
  - `bin-tests` 里 `start_with_level(…, "trace")` 的用途（为了检索日志）消失后，若入口无调用者则一并删除（P2.2-007 第 4 步）。
- **约束**：删日志不得改动任何计数口径；P2.2-004 完成后必须逐项核对快照字段与 P2.2-001 一致。
- **承接任务**：P2.2-004、P2.2-007、P2.2-014。

## D-P2.2-011 压力用例的收尾：不逐个 `client_delete`

- **状态**：`DECIDED`
- **问题**：`N` 或 `2N` 个客户端压完，要不要按常规收尾（`occupancy/delete` + `client/delete`）？
- **可选方案**：
  1. 不做逐客户端收尾，用例结束后由 `runner` 停止服务端；
  2. 逐个收尾，计入用例耗时；
  3. 收尾但排除在计时之外。
- **决策**：①。
- **理由**：
  - 每条断连都会触发清理链（含会话停止的阶段等待），几百条清理链会主导收尾时间，且与「测容量边界」无关。
  - ②③都会让报告的「实测总耗时」与断言的时间窗口混入无关开销，读者无法判断数字含义。
  - 用例是 `Isolated`，服务端随用例结束整体销毁，收尾不需要礼貌性反注册。
- **约束**：
  - 不逐个收尾这件事必须写进用例注释与报告口径，否则后来者会以为是漏了。
  - 用例必须保证 SSE 流被关闭、连接不泄漏（否则服务端停止会被拖住，见 P2.2-010 的收尾健壮性）。
- **承接任务**：P2.2-009、P2.2-010。

## D-P2.2-012 不为扩大压力规模改 Mock 节奏参数

- **状态**：`DECIDED`
- **问题**：需求举例是「3s 处理 300 次」。要不要把 Mock 的分块间隔压到 1ms，好让 `N` 正好落在 300 附近？
- **背景与证据**：
  - Mock 的节奏参数是查询串 `chunk_ms` / `stall_ms`（`src/mock/llm/scenario.rs`）；服务端调用 Provider 时无法在 `base_url` 上携带查询串（路径由 rig 追加）。
  - 默认 `chunk_ms = 10`，回复按 6 字符一帧切分，一次回复只有数帧，串行单次耗时在几十毫秒量级，`T = 3s` 对应的 `N` 在几十到一百之间。
- **可选方案**：
  1. 不动 Mock 契约；`N` 由标定得出，规模多大就是多大；
  2. 为 Mock 增加「按路径段指定分块间隔」的能力，把 `N` 拉到 300 级；
  3. 通过用例配置里的任务文本长度控制分块数量（间接控制 `L0`）。
- **决策**：①。
- **理由**：
  - 用例的价值在「边界」而不在「数字等于 300」：`300` 只是需求举例，`N` 由公式算出并写进报告，同样满足「用边界参数测试」。
  - ②要改 Mock 契约与观测面（P2.1 刚把 Mock 收进 `mock/llm/` 并约定能力不变），为一个示例数字扩大改动面不划算。
  - ③把用例的成功标准绑在提示词文本长度上，脆弱且难解释。
- **约束**：用例必须在报告里给出 `L0` 与 `N`，让读者知道本次边界落在哪个量级；若将来确实需要更大规模，另开决策改 Mock 节奏能力。
- **承接任务**：P2.2-008、P2.2-009。

## D-P2.2-013 边界用例落地的三处口径：形态 / 标定 / 内边界断言

- **状态**：`DECIDED`
- **问题**：按 README §4.1 直译落地 `stress.boundary` 时，用例既注入不了配置，也算不出能自证的门槛——实测连续两次红。
- **背景与证据**（`make test ARGS="stress"` 的一次性实测；数据取自用例报告，不读日志）：
  1. `runner::run_isolated` 的私有服务端固定用 `Server::start`（默认 `[agent]`：`max_concurrent_runs` 走 `"3C"`、`run_queue_timeout_ms` 走 120s），注入不了 `max_concurrent_runs = 1` / `run_queue_timeout_ms = 3000`，G-1-2 无法成立。
  2. 把「注册 → 会话 → 占用 → 订阅 → 发消息 → 终态」整条链路当 `L0`：实测 `L0 ≈ 113ms`，而真正被串行化的那一段只有 ~51ms；`N = 27`、`2N = 54` 全部 `run_completed`，最长排队 2675ms < 3000ms，③ 拿不到任何排队超时。
  3. 改把串行段当 `L0` 后仍会红：第一轮标定要付建库与建立 Provider 连接的冷启动，`L0` 被抬到 ~108ms，`N = 28`、`2N = 56` 依旧压不到门槛上。
  4. ② 的「末个终态 ≤ `T`」与 `N = floor(T / L0) + 1` 自相矛盾：`N × L0 > T`（实测出现 3023ms vs 3000ms 判红）。
  5. `queued_max >= N - 1` 会被「进队错峰」打掉 0 ~ 2 个（实测 5 次峰值：`N`、`N`、`N-1`、`N`、`N-2`）。
- **决策**：
  1. 用例形态用 `CaseKind::SelfServed`：用例自己起停私有服务端（私有 `AGENT_HOME` + `server::free_port()`）与私有 `MockServer`；
  2. `L0` 取「发消息 → 终态」的串行段，先跑 1 轮预热丢弃冷启动，再取 3 轮的最大值；完整链路耗时仍写进报告做对照；
  3. ② 的耗时断言上界是 `T + L0`（末个 Run 拿到许可后还要自己跑完一个串行段；该上界的收尾余量已被 D-P2.2-016 修订为 `T + max(L0 × 2, 500ms)`）；「余量」改按快照的 `wait_max_millis` 给出，因为那才是被等待预算约束的量；
  4. 队列深度断言按「在跑 + 排队」的峰值核对，留 `QUEUE_PEAK_SLACK = 4` 的进队错峰容差。
- **理由**：`N` 的公式与取值一律不动（D-P2.2-009 禁止对 `N` 放水）；改的只是「`L0` 量的是哪一段」与「断言的物理上界」。不这样改，用例要么注入不了配置，要么无论跑多少次都拿不到 ③ 的超时证据。
- **约束**：
  - `QUEUE_PEAK_SLACK` 只放宽诊断断言，**不得**用于缩小 `N`；
  - 标定的预热轮与串行段口径必须与报告里的 `L0` 一致（报告同时给出完整链路耗时供对照）；
  - ③ 必须稳定出现「执行排队超时」（实测 39 ~ 51 条 / 94 ~ 108 个客户端）。
- **承接任务**：P2.2-008、P2.2-009、P2.2-010。

## D-P2.2-014 `--async` 的落地口径：还原参数子集、输出与 PID 文件位置

- **状态**：`DECIDED`
- **问题**：README §4.2 只给了方向（「重新执行当前可执行文件、参数由配置反向构造」「日志 `<AGENT_HOME>/logs-server`」）；落地时必须确定还原哪些参数、输出文件与 PID 文件的确切位置与格式，否则用例与文档无处对齐。
- **背景与证据**：
  - `ServerConfig` 里只有 `host` / `port` / `log_level` 能还原成命令行；`runtime_events` 与 `[provider]` / `[agent]` 只能从 `AGENT_HOME/config.toml` 读。子进程继承同一个 `AGENT_HOME`，把它们摊成参数既多余又会造出第二份配置来源。
  - 服务端日志目录的实际名称是 `logs`（`lib-core::directorys` 的 `AppDirectories::logs_server`）；README 里的 `logs-server` 指的就是它，以代码为准。
  - 应用根目录只能由 `config_file`（`<root>/config.toml`）反推：`AppDirectories` 不单独暴露 root。
- **决策**：
  1. 子进程命令行只还原 `--addr` / `--port` / `--log-level`，其余配置仍由子进程从 `<AGENT_HOME>/config.toml` 读；
  2. 派生进程的 `stdout` / `stderr` 追加写 `<AGENT_HOME>/logs/stdout.log`（即 `logs_server` 目录下的 `stdout.log`）；
  3. PID 文件为 `<AGENT_HOME>/server.pid`，内容两行 `pid = <进程号>` 与 `address = <服务地址>`；写入发生在探活成功之后（D-P2.2-004）；
  4. 文件名常量在 `lib-bin-cli::server` 公开（`PID_FILE` / `STDOUT_FILE`），`bin-tests` 直接引用，不重复字面量；
  5. 用例收尾走 `bin-tests::util::process`（Windows `taskkill /F` + `tasklist`，其他平台 `kill -9` / `kill -0`）：`Drop` 兜底结束进程，`stop` 断言它真的消失。
- **理由**：可还原的只有这三项；多还原一项就要在配置面与命令行之间维护第二条同步路径，与「地址只有一个来源」冲突。PID 文件用两行 `key = value`，人工可读、用例可解析。
- **约束**：不新增配置字段与环境变量；`--async` 不进入配置解析（由调用方读 `ServerArgs::asynchronous` 分支）；PID 文件与输出文件的路径与格式一旦写进用例，改动需同步 P2.2-015 的文档。
- **承接任务**：P2.2-011、P2.2-012、P2.2-013、P2.2-015。

## D-P2.2-015 `--async` 的输出转发与 Windows 标准句柄非继承

- **状态**：`DECIDED`
- **问题**：`--async` 派生后 CLI 立刻退出，用户与应用都看不到子进程启动过程；且 Windows 上常驻进程会继承
  CLI 的可继承句柄，把 CLI 的输出管道写端一直握着，`| grep`、`$(…)` 这类用法会挂到服务端退出（KI-P2.2-001）。
- **背景与证据**：
  - 实测 `AGENT_HOME=… bin-agent server --async --port 20204 | cat` 20 秒不返回（`timeout` 退出码 124）；
    `bin-tests` 的 `cli.async_server` 也因此被拖到 60 秒用例超时，随后 `make … | tail` 因同一句柄挂住 20 分钟以上。
  - Windows 的 `CreateProcess` 默认把父进程所有可继承句柄传给子进程；把子进程 `stdin` / `stdout` / `stderr`
    重定向到 `null` / 文件**不能**阻止**其它**可继承句柄一并被继承。
  - `std::os::windows::process::CommandExt::inherit_handles` 仍是 unstable
    （`windows_process_extensions_inherit_handles`），稳定版没有等价开关。
- **决策**（按需求方调整意见落地）：
  1. **转发**：派生后 CLI 不立即返回；在轮询探活接口期间，把子进程输出文件里**本次派生之后新增**的内容
     （按派生前文件长度作起点）转发到自身 `stderr`，探活通过或失败后再各泵一次，然后才打印接入信息或报错。
     转发写 `stderr`，保证 `stdout` 上只有 `PID` / 服务地址 / 日志目录 / PID 文件这四行，脚本可解析。
  2. **句柄隔离**：Windows 分支新增 `hide_standard_handles()`，在派生前调用 kernel32 的
     `GetStdHandle` + `SetHandleInformation(HANDLE_FLAG_INHERIT, 0)`，把本进程的标准输入 / 输出 / 错误
     三个句柄置为非继承。**授权引入 `unsafe` FFI**：仅两个系统调用、不新增第三方依赖，`unsafe` 块附
     SAFETY 说明且只操作自身标准句柄（不解引用、不转移所有权）。Unix 分支为空实现。
  3. `cli.async_server` 改回**管道读取**并给读取加 5 秒时限：句柄隔离一旦被去掉，用例以
     「CLI 的 stdout 管道在 5s 内没有到 EOF」失败，而不是挂到用例超时——用例因此成为该修复的回归哨兵。
- **理由**：转发解决「看不到启动过程」，句柄隔离解决「管道不关闭」——两者缺一，`| grep` / `$(…)` 仍然不可用。
  把转发写 `stderr` 是为了不破坏「`stdout` 四行接入信息」这一可解析契约。
- **约束**：转发是尽力而为（下游管道已关闭时不得让父进程失败）；转发只覆盖就绪之前，常驻期间输出仍只落文件；
  正式构建的 `--async` 行为与非 `metrics` 构建一致（与特性无关）。
- **替代方案（未采纳）**：仅记已知限制（管道场景挂住）；仅做句柄隔离、不转发（看不到启动失败原因）。
- **承接任务**：P2.2-012、P2.2-013、P2.2-015（文档同步）。

## D-P2.2-016 内边界总耗时上界的收尾余量（KI-P2.2-002 的处置口径）

- **状态**：`DECIDED`
- **问题**：`stress.boundary` 在 `--all` 并发下偶发破「② 总耗时 ≤ `T + L0`」（KI-P2.2-002），
  要不要放宽这条上界？放宽到什么程度才不构成「对 `N` 放水」？
- **背景与证据**：
  - D-P2.2-013 把上界定为 `T + L0`：`L0` 是**用例独占服务端**时标定的末段耗时，`--all` 下 CPU 被
    其他用例抢占，末个 Run 自己跑的那一段会被拉长，于是破上界（实测 3106ms vs `T + L0` = 3054ms，
    超出 51ms，而 `L0` 只有 54ms）。
  - 门槛本身没有被击穿：同一次失败里 `limit.timeouts == 0`、`wait_max 2913ms < T = 3000ms`、
    `running_max == 1`、`N` 个客户端全部 `run_completed`。
  - 单跑（`make test ARGS="stress"`）连续 3 次全绿，说明破的是「并发下末段被拉长」这一项，与公式无关。
- **可选方案**：
  1. 上界改为 `T + max(L0 × 2, 500ms)`，`N` 与公式一律不动；
  2. 让 `self` 型用例在调度层独占运行（串行化），代价是 `--all` 墙钟变长；
  3. 不改，接受偶发红并在阶段报告里注明「单跑为准」。
- **决策**：①。
- **理由**：
  - ②要为一条诊断断言改动测试调度层，影响全部用例的墙钟，收益与代价不成比例。
  - ③让一条**会红的用例**长期留在全量里，等于把「偶发红」变成常态，与 P2.1 的教训相反。
  - ①只放宽「总耗时」这条诊断断言：真正约束边界的 `N`、`limit.timeouts == 0`、`wait_max < T`、
    `running_max == 1` 全部不动，因此不构成对 `N` 的放水（D-P2.2-009 仍成立）。
- **余量口径**：
  - `TAIL_FACTOR = 2`：末段在并发下被拉长的量级按 `L0` 的一倍计（独占标定 → 并发下最多两倍）。
  - `TAIL_FLOOR = 500ms`：调度延迟与 CPU 抢占的那部分与 `L0` 无关，用一个固定托底余量覆盖；
    取 500ms 的依据是上面 51ms 的实测超出量再留一个量级。
  - 上界由 `bin-tests::util::stress::inner_ceiling(per_run, budget)` 唯一给出，用例文件不出现数字。
- **约束**：
  - 余量只能用于「总耗时」这条诊断断言；不得用于缩小 `N`，也不得用于放宽 `limit.timeouts == 0`。
  - 若余量仍被打红，说明并发干扰已超出同量级，按 KI 重新决策，不得继续加大余量。
- **承接任务**：P2.2-016（回归基线）。
