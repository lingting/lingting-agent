## D-P6-001 检查点粒度：只落在已提交的边界

**状态**：拟定

**背景**：`agent-runtime` 的现状是「一轮工具执行完成后，助手消息 + 每条工具结果 + 审计行在同一个事务里提交」（D-P3-024）。因此「已提交的边界」天然就是检查点的唯一天然位置。

**决策**：检查点只落在三种边界，`phase` 取值固定：

| phase | 落点 | 语义 |
|---|---|---|
| `MODEL_DONE` | `run_started` 之后，以及每轮模型请求返回且收尾事务提交之后 | 「到此为止的模型轮次都已落库」 |
| `TOOLS_DONE` | `run_round` 的 `append(messages)` 提交之后 | 「本轮工具批次已全部落库」 |
| `AWAITING_CONFIRM` | `record_tool_call(pending)` + `RUNNING → WAITING` 提交之后 | 「Run 停在确认点」 |

顺序 **一 提交，二 检查点**：反过来的话，检查点会指向一个还没提交的边界，恢复时就会认为「进度已到但数据没到」。

**理由**：检查点的作用只有一个——告诉恢复流程「从哪条消息之后继续」。这个信息只有在事务提交后才是真话；粒度高过事务边界只会产生「半批次」这种既不能重放也不能跳过的不确定态。

**被否方案**：

| 方案 | 否决原因 |
|---|---|
| 每个 token 增量 / 每条 `message_delta` 落检查点 | 写放大到不可接受（一次 Run 上千次写库），而增量本身不构成可恢复边界——模型输出不是幂等的，重发一次就全变了 |
| 只在 Run 级落（开始 + 结束） | 无法定位进度，恢复等价于「从头再跑一遍」，与本子阶段目标相反 |
| 每个工具调用单独落检查点 | 粒度比事务边界细：一次 Run 有 N 个调用就多 N 次写，但恢复时这些调用仍属同一批次，无法单独「跳过第 2 个、继续第 3 个」 |
| 把检查点写进事件文件 | 见 D-P6-002 |

**影响面**：`agent-runtime`（三个写入点）、`service-core`（追加检查点的唯一入口）、判据 `C-1` / `C-2`。

## D-P6-002 事实源：SQLite 是唯一恢复依据，事件文件不是

**状态**：拟定

**背景**：P1.1 把事件文件定义为「事件的唯一事实源」。这句话对**事件**成立，但它不能被推广成「Run 进度的唯一事实源」，原因有三条硬事实：

1. 轮转（`max_sessions = 200` / `max_bytes = 512 MiB`）会**删除整个会话目录**，其中包括含可恢复 Run 的文件；
2. 事件 `seq` 由写者持有，**每次运行时会话从 0 重新计数**——同一 Run 跨进程的序号本来就不连续；
3. 事件文件逐条 flush 但**不 `sync_all`**，强杀后末尾可能缺行。

**决策**：恢复只读 SQLite（`runs` / `messages` / `tool_calls` / `run_checkpoints`）。事件文件继续承担客户端重放与排障，不参与任何恢复判定；恢复产生新的运行时会话与新的文件，客户端按 `run_id` 归并两段事件。

**理由**：可恢复性必须建立在「持久化语义明确」的数据上：SQLite 的事务边界就是「已提交」的定义，而事件文件的写入语义是「尽量写、不保证尾部完整」。把两者混用会得到一个既不能证明进度、也不能保证完整的事实源。

**被否方案**：

| 方案 | 否决原因 |
|---|---|
| 事件文件作为恢复事实源 | 轮转会删除、`seq` 每次重置、不 `sync_all`——三条都直接破坏「已提交边界」的定义 |
| 数据库 + 事件文件双写，以事件文件为准 | 两种事实源必然漂移（轮转、强杀时机不同），排障成本高于收益 |
| 两者交叉校验后才允许恢复 | 把可恢复性耦合到「随时会消失的临时数据」上：事件被轮转删掉就等于这个 Run 永远不能恢复 |
| 恢复时把事件文件回填进数据库 | 引入第二套写入路径与重复计数风险，且事件本来就由数据库状态产出，属循环 |

**影响面**：`manager-agent`（恢复不读事件目录）、`bin-tests` 的 `resume.crash`（`R-8` 显式断言「删掉事件目录仍能恢复」）、`docs/api/session.md` 的时间线说明（待同步）。

## D-P6-003 检查点格式与跨版本兼容

**状态**：拟定

**背景**：检查点一旦落库，就会遇到「新代码读旧数据」和「旧代码读新数据」两种情形。`lib-db` 只做前进迁移，不提供 down。

**决策**：

1. `CHECKPOINT_FORMAT_VERSION: u32 = 1`，全仓只定义一处，写入时同时写进 `format_version` 列与 payload。
2. 解码规则：
   - `== 当前版本` → 严格解码：**未知字段忽略**（向前扩展留余地）、**缺字段报错**（不猜默认值）；
   - `> 当前版本` → `Unsupported`：判不可恢复，Run 落 `FAILED` + 固定文案；
   - `== 0` 或缺失 → `Corrupt`：同上。
3. **不记录上下文指纹**（system prompt、Skill 集合、Provider 配置的摘要）。恢复时 Context 重新组装，并在步骤历史里显示「本次恢复重新组装了上下文」。
4. 不为未来版本预留兼容分支：没有 `match 其它版本 => 尽力解释` 这种兜底。

**理由**：单机产品的升级方向是单向的（用户升级后不会回退到旧 binary 读新库）。真正的风险是「新代码遇到一个它没见过的版本」——这种情况唯一安全的动作是停止并给出原因，而不是猜。忽略未知字段则保证「加字段不需要升版本」。

**被否方案**：

| 方案 | 否决原因 |
|---|---|
| 不带版本号，宽松解码 | 字段语义一变就会静默误读，恢复出一条错误的轨迹，比直接失败更糟 |
| 记录完整上下文快照，保证恢复后逐字节一致 | 体积大；且与 P5 的 Skill 集合、`AGENTS.md` 的现场读取（P2 的既有口径）冲突——上下文本来就该每次重新组装 |
| 双向兼容（旧代码也能读新检查点） | 单机前进迁移下没有这个需求，只会增加分支与测试面 |
| 遇到未知版本就从头重跑 | 隐藏了「数据不可解释」这件事，且可能重复副作用 |

**影响面**：`agent-core`（`RunCheckpoint` / `CheckpointPhase`）、`service-core`（编解码）、`agent-runtime`（错误文案）、判据 `C-5` / `C-6`。

## D-P6-004 中断态的表达：新增非终态 `PAUSED`

**状态**：**已确认**（本轮定案：接受这一契约变更）

**背景**：目前启动自愈把残留的 `RUNNING` 一律落成 `FAILED`（`HEAL_RUNNING`）。要能恢复，就必须让这个状态既不是终态、也不能被执行队列自动拾取。

**决策**：`RunStatus` 增加 `Paused`（wire 值 `PAUSED`），语义三条：

1. **非终态**：可以被恢复成 `RUNNING`，也可以被取消成 `CANCELLED`；
2. **只能由启动自愈产生**：写入 SQL 只有一处，且带 `WHERE status = 'RUNNING'`；
3. **不占并发许可、不阻塞同会话后续 Run、不计入 `runningRunCount`**。

同时把状态集合收敛成 `is_terminal()` / `is_active()` / `can_cancel()` 三个函数，禁止调用点各自写 `matches!`。

**理由**：备选方案（复用 `FAILED` + 新列）会让「终态唯一」这条从 P2 起就成立的约束失去意义——客户端每个分支都要额外读列判断「这个 FAILED 是不是可恢复的」。新增枚举值的影响面是明确的、可枚举的（两份 SDK + TUI + WebUI），而语义分叉的影响面是持续扩散的。

**被否方案**：

| 方案 | 否决原因 |
|---|---|
| 复用 `FAILED` + `resumable` 列 | 「终态唯一」被稀释：`FAILED` 既可能是真失败也可能是可恢复中断，取消/恢复/统计三处都要读列，客户端与 API 消费者也都要读列 |
| 复用 `WAITING` | 语义冲突：`WAITING` 是「等某个客户端回传确认」（有 `pending_tool_call_id`），恢复不等任何客户端回传，且 `WAITING` 有挂起唤醒路径会误命中 |
| 新增终态 `INTERRUPTED` | 方向相反：终态不可恢复，与「崩溃后可继续」的目标直接矛盾 |
| 不复用、也不新增，改成「Run 表加 is_paused 布尔」 | 与状态机互斥，两次写不同步就会出现「status=RUNNING 且 is_paused=true」这种不可解释的组合 |

**影响面**：`agent-core`、`service-core`（条件更新）、`manager-agent`（自愈）、`lib-bin-tui` / `lingting-agent-ui`（状态映射）、两份 SDK、`docs/api/session.md`（待同步）、判据 `S-1` ~ `S-4`。

## D-P6-005 崩溃恢复与「Run 终态唯一」的关系

**状态**：拟定

**背景**：P2 起「终态写入一律条件更新，影响 0 行即说明已被取消或已终态」（D-P2-030）。恢复机制若另开一条收尾路径，就可能出现第二次落终态。

**决策**：

1. 终态集合不变：**只有** `COMPLETED` / `CANCELLED` / `FAILED`。`PAUSED` 是唯一的可恢复中间态，且不是终态。
2. 恢复成功与正常完成**走同一条收尾事务**（写助手消息 + 终态 + token 用量），不新增第二条函数。
3. 终态行禁止被任何路径改写：`PAUSED` 只从 `RUNNING` 产生；终态不回到 `PAUSED`，也不被二次自愈改写。
4. 「一个 Run 一个结局」的判断标准写成可检条件：同一 `run_id` 的终态只能出现一次，且 `messages` 里该 Run 的助手消息条数与正常完成的 Run 同形（只有一条）。

**理由**：`PAUSED` 只解决「中断期间怎么描述」，不改变「结局唯一」这条契约。把恢复做成「另一条收尾路径」是最容易出双份数据的地方——恢复后的收尾、终态事件、token 统计都必须与正常路径共用同一段代码，否则两处会慢慢分叉。

**被否方案**：

| 方案 | 否决原因 |
|---|---|
| 允许 `FAILED` 被恢复并改写为 `RUNNING` | 直接破坏唯一结局；且 `FAILED` 的 `error` / `finished_at_ms` 语义会变成「可能是过程量」 |
| 恢复走独立收尾路径（`complete_resumed()`） | 双份收尾逻辑必然分叉：token 累加、事件序列、检查点清理都会不一致 |
| 定时任务自动重试残留 `RUNNING` | 无人值守地重放可能已发生的副作用，且与 D-P6-009 的触发模型冲突 |

**影响面**：`service-core`（收尾与条件更新）、`agent-runtime`（恢复分支合流）、`manager-agent`（自愈）、判据 `S-3` / `S-5` / `S-6`、`R-4` / `R-9`。

## D-P6-006 恢复的幂等与重复执行边界

**状态**：拟定

**背景**：工具执行的副作用（HTTP 写、文件写、外部状态变更）**不可回滚**。任何「保证只执行一次」的承诺都需要工具侧的幂等键协议与分布式事务，超出本子阶段范围。

**决策**：幂等只定义在**状态机与轮次**层面，明确不承诺副作用只发生一次：

1. **推进幂等**：`PAUSED → RUNNING` 是条件更新，同一 Run 在并发/连续触发下只有一次生效；未命中的一次直接跳过（不产事件、不改行）；
2. **轮次幂等**：已提交的轮次不重跑（`messages` 里已配对的不再执行）；
3. **调用不重放**：未配对（最后检查组里缺结果）的调用**一律不执行**，改为落一条 `ERROR` 审计 + 一条 TOOL 结果消息，文本「上次执行被中断：<简短原因>」（D-P6-007）；`PENDING` 开始标记只用于让「有开始无结束」可见、并区分通知口径，**不用来放行重放**；
4. **副作用边界**：在阶段报告里显式登记为 `KI-P6A-xxx`——「工具执行期间崩溃可能导致一次副作用没有对应审计行」。

**理由**：把「恢复」说成 exactly-once 是错的；而一旦允许某些调用重放，实现就必须逐个工具判断「这个副作用能不能重复」，判断错了就是静默的双写。定案选择更保守的一侧：**状态机至少一次推进、每一次工具调用至多一次尝试**，边界是「有没有提交」而不是「工具有没有声明可重放」。

**被否方案**：

| 方案 | 否决原因 |
|---|---|
| 端到端 exactly-once（引入工具幂等键 + 补偿事务） | 需要给每个第三方工具定义幂等键协议，且补偿本身可能失败；属 6E 或更后的议题 |
| at-least-once（未配对的调用一律重放） | 会重复 HTTP 写与文件写，且模型无法感知重复；对大模型调用链是雪崩式放大 |
| 不做幂等（重复 resume 各跑一条执行流） | 同一 Run 出现两条执行流 = 两份助手消息 = 数据损坏 |
| 恢复时清空该 Run 的未配对调用并从头开始 | 保留「已提交轮次」与「从头」两种语义混用，模型会看到自相矛盾的轨迹 |

**影响面**：`agent-runtime`（恢复分支与中断通知）、`service-core`（条件更新与 `PENDING` 收尾）、判据 `R-3` / `R-5`。**`agent-tool` 无契约变更**（不新增 `replayable`）。

## D-P6-007 副作用未知的调用：一律不重放，只通知中断与简短原因

**状态**：**已确认**（本轮定案：不重复执行，直接通知崩溃并附简短原因）

**背景**：崩溃时可能出现三种形态：① 调用已配对（有 TOOL 消息）；② 调用有 `PENDING` 开始标记、没有结果；③ 旧库行没有 `PENDING` 标记。②③ 都意味着「这次调用可能已经执行过」。任何重放都可能把已经发生的副作用再做一次。

**决策**：

| 形态 | 处置 |
|---|---|
| 已配对 | 不执行，直接进轨迹 |
| `PENDING`（有开始标记、无结果） | **不执行**；落一条 `ERROR` 审计 + 一条 TOOL 结果消息 |
| 无 `PENDING`（旧库行） | **不执行**；同上，文本不带「可能已执行」的限定 |

通知文本（单一产点，`agent-runtime/src/error.rs`）：

```text
上次执行被中断：<简短原因>
```

`<简短原因>` 取自 `runs.interrupted_reason` 的白名单映射（当前只有「服务重启」这一类），**不拼接**工具名以外的任何内容、不带调用参数原文、不含绝对路径、不含日志片段。审计状态用 `ERROR`（复用 P3 既有取值，**不新增** `ToolCallStatus` 取值）。

同时对外可见的两处补充（都不是新事件）：

1. `api/run/history` 的 `interruptedReason` 返回同一句简短原因；
2. 恢复后首个 `run_started` 事件的 `error` 字段带上同一句简短原因（复用既有字段，不新增事件类型）。

**理由**：

- 「不重放」是唯一不需要给每个第三方工具裁定「副作用能不能重复」的规则，判断错误面为零；
- 但「什么都不说」同样错：模型会以为这一轮没有工具结果，从而凭空继续。显式 TOOL 结果让模型知道「上次没跑完」，是否重新发起由模型按任务需要决定，而不是由恢复机制偷偷决定；
- 「附加简短原因」让模型与用户都能区分「执行失败」与「执行被中断」，且原因来自库里已有的固定文案，不引入新的错误体系。

**被否方案**：

| 方案 | 否决原因 |
|---|---|
| 只重放可重放工具（如只读工具），其余回灌「结果未知」 | 需要给工具补「可重放」自述并逐个裁定，判断错一次就是静默双写；只读重放换来的收益（省一次模型轮次）不值这个风险 |
| 一律重放 | 可能重复 HTTP 写 / 文件写，且对第三方工具完全没有保护 |
| 静默丢弃未配对调用 | 模型会认为「这一轮没有工具结果」，凭空继续，行为不可解释 |
| 用 `ToolRisk::ReadOnly` 推导可重放性 | 风险是权限维度（是否默认拒绝），不是可恢复维度；MCP 工具的 `file_access` 来自配置，不构成安全证明 |
| 新增 `ToolCallStatus::UNKNOWN` 枚举值 | 契约破坏面（两份 SDK + 客户端 + 审计查询）大于收益，且与 P3 的分类表语义重叠；`ERROR` + 固定文案已足够表达 |
| 中断原因直接拼接内部错误串（含路径 / 堆栈） | 会把绝对路径与内部细节泄漏进模型上下文与接口响应 |

**影响面**：`agent-runtime`（恢复分支、通知文本、`run_started.error`）、`agent-tool`（**无契约变更**）、`service-core`（`PENDING` 收尾与 `history` 读取）、判据 `R-5` / `E-4`。

## D-P6-008 工具审计口径：`PENDING` 行不进查询结果

**状态**：拟定

**背景**：`PENDING` 开始标记前移后，库里会出现「已开始、未结束」的行。若查询接口原样返回，客户端会看到永不结束的调用。

**决策**：`api/tool/audit/list` **不返回** `PENDING` 行（查询侧加状态过滤）；行在库内保留，供恢复判定使用；返回结构只新增 `startedAtMs`，其余字段与 P3 结案时逐字段一致。

**理由**：审计查询的语义是「已发生的调用结果」，`PENDING` 是过程量而不是结果。把它暴露出去会让每个消费者都要处理「没有结果的结果」这种形态，而恢复判定又不需要通过 HTTP 读它。

**被否方案**：

| 方案 | 否决原因 |
|---|---|
| 返回 `PENDING` 行 | 客户端看到永不结束的调用；前端必须额外处理空结果状态 |
| 把 `PENDING` 提升为公开契约状态 | P3 已明确 `PENDING` 只出现在挂起等待确认期间、不出现于 `tool_call_completed` 事件；扩到查询契约会和事件契约打架 |
| 不落 `PENDING`，改用独立「开始标记表」 | 多一张表与一套清理逻辑，而 `tool_calls` 已经有唯一键 `(run_id, tool_call_id)`，天然适合做标记 |
| 恢复时靠 `started_at_ms` 之外的时间推断 | 时间推断不可靠（时钟回拨、并发批次），必须有显式状态 |

**影响面**：`service-core`（查询过滤）、`lib-web`、判据 `K-2`。

## D-P6-009 恢复的触发方式：占用 + 向该会话发一条消息

**状态**：**已确认**（本轮定案：不新增恢复接口）

**背景**：Run 只在「所属会话被占用」时执行（D-P1.1-004）；占用是进程内状态，不跨重启（`persist.occupancy_reset`）。而 P1.1 的 Run 触发点本身就是「会话被占用 + 消息创建」，恢复正好可以搭在这条既有路径上。

**决策**：恢复**只有一个触发条件**：

```text
会话已被客户端占用  ∧  该会话收到一条新消息（api/message/create 成功）
```

具体规则：

1. 消息创建成功后，该会话的执行队列按固定顺序处理：**先恢复全部 `PAUSED` Run**（按 `updated_at_ms` 升序），**再执行 `QUEUED` Run**（本次消息产生的新 Run 在后）；
2. 恢复不使用新消息的正文：被恢复的 Run 继续使用它自己那条原始用户消息（检查点里已记录消息上界）；
3. 每次恢复都经 `PAUSED → RUNNING` 条件更新，只生效一次；同一批里已被别人推进的 Run 直接跳过；
4. **不新增** `api/run/resume` 接口、**不新增** `resume_on_occupy` 之类的配置项；
5. **占用本身不触发恢复**：只 `occupancy/create` 而不发消息，`PAUSED` Run 保持原样；取消仍走 `api/run/cancel`（D-P6-005）；
6. 不引入后台 sweeper / 定时恢复 / 无人值守 worker。

**理由**：

- 恢复不是「新动作」，而是「这条会话的对话继续往下走」的前置条件。把它挂在「发消息」上，用户的心智模型最简单：**发一条消息，之前没跑完的那段就接着跑**；
- 触发条件复用 P1.1 既有的「占用 + 消息 → 队列唤醒」路径，不新增接口、不新增配置、不新增调度层，客户端零改动（TUI / WebUI 只是显示中断态并提示「发送消息即可继续」）；
- 「占用本身不恢复」是有意的：占用可能只是用户点开会话看一眼，此时无人值守地重跑一段可能带副作用的流程并不合适。

**被否方案**：

| 方案 | 否决原因 |
|---|---|
| 新增显式 `api/run/resume` | 多一条接口、多一套错误码与拒绝路径，且客户端要实现「占用 → 查 PAUSED → resume」三步；而「发消息」本来就必须做，白得一个触发点 |
| 占用即自动恢复 | 占用可能只是「打开看看」，此时无人值守地继续执行不合适；也让「谁触发」变得隐式 |
| 启动时自动恢复（不等占用） | 执行队列随运行时会话创建（P1.1），没有占用的会话根本没有队列；强行恢复等于绕开 D-P1.1-004 |
| 后台 sweeper 定期扫描 `PAUSED` | 新增调度层，且会无人值守地重放副作用；事件也没有接收方（SSE 无连接） |
| 恢复即创建占用（服务端代占） | 占用是客户端身份（`client_id`）的绑定关系，服务端代占会让「谁在看」失去意义 |
| 用新消息的正文替换被恢复 Run 的输入 | 会把两段对话混成一个 Run，且模型看到的消息序列与库里不一致 |

**影响面**：`service-core`（消息创建后的恢复登记、`PAUSED → RUNNING`）、`manager-agent`（队列处理顺序：先恢复后 `QUEUED`）、`lib-web`（`api/message/create` 的副作用说明，**不新增路由**）、客户端（只显示与提示）、判据 `R-1` / `R-2` / `R-4` / `E-1` / `E-2`。

## D-P6-010 检查点写失败的处置：fail-fast

**状态**：拟定

**背景**：检查点写入与「已提交边界」在同一连接池路径上，写入可能因磁盘满、锁冲突、数据库损坏失败。

**决策**：检查点写失败 → 立即把 Run 落 `FAILED`，`error` 用固定文案，且**不写助手消息**；不重试写入、不降级继续。

**理由**：检查点的价值就是「可恢复性的证明」。写失败还继续跑，等于在用户不知情的情况下把可恢复性降级成「不可恢复」，而 Run 又会正常完成——这种「看起来成功、实际失去保护」的状态是最难排查的。失败要显式。

**被否方案**：

| 方案 | 否决原因 |
|---|---|
| 继续执行，只是没有检查点 | 可恢复性无声消失；`C-7` 无法取证；用户无法知道 |
| 重试写入（含指数退避） | 把写放大与超时引入循环；且失败原因（磁盘满）通常不会因重试而好转 |
| 只记日志并继续 | 日志不是数据来源（`AGENTS.md` 采集条款），且状态对外不可见 |
| 落 `CANCELLED` 而不是 `FAILED` | 语义错误：中断不是用户造成的，原因必须能被读到 |

**影响面**：`agent-runtime`（三个写入点）、`agent-runtime/src/error.rs`（固定文案）、判据 `C-7`。

## D-P6-011 恢复与并发许可、会话占用的关系

**状态**：拟定

**背景**：`RUNNING` 才代表「正在执行」，全局许可在 `QUEUED → RUNNING` 之前取得（P2-025）；`PAUSED` 不在执行，也不该占位。

**决策**：恢复走**与正常执行完全相同的路径**：占用会话 → 进入该会话的执行队列 → 取全局许可 → `PAUSED → RUNNING` → 与正常 `drive` 合流。`PAUSED` **不占**并发许可、**不阻**同会话后续 Run、**不计入** `runningRunCount`。

**理由**：恢复不应该有特权。给它单独的许可池或绕过队列，都会造出「两套限流、两套指标、两套顺序保证」，而这两套迟早会给出互相矛盾的观测结果。

**被否方案**：

| 方案 | 否决原因 |
|---|---|
| 恢复不受并发上限约束 | 用户可以靠「反复强杀 + 恢复」绕过限流 |
| 为恢复单独开一个许可池 | 第二套限流：`runningRunCount`、排队超时、压力用例的口径全部失效 |
| 启动即恢复并跳过占用 | 违反 D-P1.1-004；事件没有接收方；`R-1` 的判定动作也不再成立 |
| `PAUSED` 计入 `runningRunCount` | 探活语义被污染：进程里根本没有执行中的 Run |

**影响面**：`manager-agent`（队列与许可）、`service-core`（统计 SQL）、`agent-runtime`（`drive` 入口）、判据 `S-7`、`R-1`。

## D-P6-012 Task Recovery 的重试归属与上限

**状态**：拟定

**背景**：现状只有**工具级**重试（`Tool::retryable` + `limits.max_retries`），模型调用失败一律直接 `FAILED`。P6 阶段目标要求「长任务的分段执行与失败重试；不可重试失败给出明确终态与原因」。

**决策**：

1. 「分段」= 轮次边界（`max_tool_rounds` 与检查点边界），**不引入新的任务调度层**；
2. **Run 级重试**只作用于「同一次 LLM 请求」：`[agent] run_max_retries` 缺省 `0`（保持现有行为），配置为正整数时按次数重试，每次累加 `metrics` 计数；不重新入队、不重跑已提交轮次；
3. 失败分类表集中在一处：可重试（上游瞬时错误、`LlmError` 传输类、工具 `Retryable`）／不可重试（认证、上下文超预算、轮次用尽、轨迹损坏、检查点不可用或写失败、取消）；
4. 不可重试 → 立即终态 + 固定原因，不消耗重试预算；
5. **不引入** Run 级自动重新入队（需要重跑就由用户显式再发消息）。

**理由**：缺省 `0` 是关键——重试会改变既有失败的时间与语义（既有用例直接断言 `FAILED`），把它做成「默认就开」属于静默行为变更。而「重新入队」会让已提交的轮次、事件序列、消息 `seq` 全部需要重算，风险远大于收益。

**被否方案**：

| 方案 | 否决原因 |
|---|---|
| 装配层重新入队（把 Run 放回 `QUEUED` 再跑一遍） | 会重跑已提交的轮次，产生重复助手消息；事件与 `seq` 也要重算 |
| 缺省重试 3 次 | 静默改变既有失败语义与用例断言；用户看到失败的时间变长，却不知道为什么 |
| 无限重试 / 长退避 | 长任务饥饿，永远给不出终态，与「明确终态」要求相反 |
| 只做工具级重试、不做任何 Run 级重试 | P6 的阶段目标明确要求「失败重试」，且上游瞬时错误（连接重置、5xx）本身没有工具参与 |

**影响面**：`agent-runtime`（`drive` 的失败分支与分类）、`types-core` / `lib-bin-cli`（两个新配置项 `run_max_retries` / `run_retry_backoff_ms` 与校验）、`metrics`、判据 `E-1` / `E-2`（拒绝路径）、`K-4`（`run` / `runtime` 回归）。

## D-P6-013 事件文件轮转是否保护含 `PAUSED` 的会话目录

**状态**：已否决（保留）

**背景**：轮转按会话目录计量、按最旧先删，`protected` 只包含「正在占用 / 写入中」的目录。若一个会话有 `PAUSED` Run，它的事件目录可能在用户回来之前被删掉。

**提出的方案**：把「含 `PAUSED` Run 的会话目录」纳入 `protected`，保证中断前的重放数据不被清理。

**决策**：**不采纳**。轮转语义与默认值（`max_sessions = 200` / `max_bytes = 512 MiB`）保持不变。

**理由**：`PAUSED` 没有超时、可以长期存在（这正是「可恢复」的含义）。一旦把它纳入 `protected`，目录就会永远不回收，`max_bytes` 上限被击穿——为了保留「重放用的临时数据」而破坏「磁盘不会无限增长」这条更硬的保证，代价不对等。恢复本来就不依赖事件文件（D-P6-002），因此清理它不影响可恢复性。

**如果将来要重开**：前提是「事件层也要能追溯中断前的完整重放」，那时应该给 `PAUSED` 加明确的保留期（例如 7 天）并计入轮转统计，而不是无条件保护。

**影响面**：无代码改动；记录在案，避免后续重复提出。
