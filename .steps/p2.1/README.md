## 二、阶段边界

### In Scope

- 测试进程内的**同步阻塞点**审计与消除（`async` 上下文里的 `std::thread::sleep`、阻塞调用、占用 worker 的等待）。
- 服务端**串行点**审计与修复：全局互斥范围、持锁跨 `await`、锁表只增不减、事件写入与转发的批量化、Run 全局许可的排队行为。
- 服务端**可观测性**：Run 排队与执行耗时、断连处理链耗时、事件落盘与转发耗时、数据库取连接等待、下行通道满（判流废）次数。
- `bin-tests` 内部模块迁移与 import 收敛（纯移动，不改行为）。
- `llm.mock` 用例 helper 归位、Mock 观测 helper 去重、模块文档纠错。
- **并发配置**：`[agent] max_concurrent_runs` 支持核数倍数写法（`2C`）与 `3C` 默认值（P2.1-015，排在 G-1 结案之后）。

### Out of Scope

| 不做的事 | 说明 |

### 与 P2 的硬约束

1. **事件通路不变**：先落盘 flush，再转发到 `api/client/stream`；文件是事实源。
2. **同会话串行不变**：同一会话同一时刻最多一个 `RUNNING` Run（P1.1 执行队列）。
3. **断连顺序语义不变**：`client_closed` 帧 → 反注册 → 停运行时会话 → 撤回占用，顺序不可交换（P1.1 README 7.2）；只允许把「全局串行」收窄为「按客户端串行」。
4. **不引入新的环境变量**：测试仍通过 `AGENT_HOME` 下的 `config.toml` 与 `bin-tests` 的 `Server::start_with` 注入配置。
5. **依赖不扩散**：`bin-tests` 与本阶段触及的业务 Crate 不得为了排查引入运行时框架；新增依赖需 D-P2.1-001 决策。

## 三、K-1 根因分析（首轮代码审查结论）

### 3.1 已确认的串行点与量级判断

| 编号 | 串行点 | 位置 | 是否阻塞 / 跨 `await` | 量级判断 | 当前结论 |
|---|---|---|---|---|---|
| S-1 | TUI 用例的同步轮询 `std::thread::sleep` | `crates/lib-bin-tui/src/testing.rs`（`Harness::wait_until`）被 `cases/tui/*.rs` 在 `async fn` 内直接调用 | **是**：同步 sleep 阻塞当前 Tokio worker，最长到用例等待上限（20s 级） | 每次阻塞 1 个 worker；默认并发 18 与 runtime worker 数同阶 | **主因候选（H-1）** |
| S-2 | 断连处理链全局互斥 | `manager-agent/src/runtime/handler.rs` 的 `CHAIN: tokio::sync::Mutex<()>`，`process` 全程持锁 | 是：持全局锁执行整条清理链 | 单次清理含 DB 取消、执行队列收尾（超时 5s）、写者 flush | **次因候选（H-2）** |
| S-3 | 清理链持会话锁跨 `await` | `handler.rs::clean`：`session_lock().lock().await` 后 `stop_session().await` | 是：会话锁内做 DB 写 + `executor.stop`（≤5s）+ `writer` 收尾 | 同一会话的占用 / 释放 / 断连互相排队 | **次因候选（H-2）** |
| S-4 | 全局 Run 许可 | `agent-runtime/src/port.rs`：`Semaphore(max_concurrent_runs)`，默认 4 | 排队即停；排队超时 120s 落 `FAILED` | 18 条并发用例共享服务端时，同时最多 4 个 Run 在跑 | **待指标确认（H-3）** |
| S-5 | 会话锁表只增不减 | `runtime/registry.rs` 的 `session_locks: HashMap<String, Arc<Mutex<()>>>`，只 `entry().or_default()`，无删除 | 取锁走**写锁**（与全部读操作争用） | 每个新会话永久留一把锁；长跑进程内存单调增长 | **确定缺陷（H-4）** |
| S-6 | 事件逐条 `spawn_blocking` + flush | `runtime/session.rs::write_event`、`journal.rs::append` | 不持锁跨 await（锁在阻塞线程内），但每帧一次阻塞任务与一次 `flush` | 磁盘页缓存写，单帧微秒级；每 Run 数十帧 | **待指标确认（H-3）** |
| S-7 | 注册表整表单 `RwLock` | `runtime/registry.rs` 的 `inner: Arc<RwLock<Registry>>`，所有客户端 / 占用 / 通道读写共用 | 不跨 `await`（已按 README 规则先取快照再放锁） | 单次操作微秒级；读多写少 | **待指标确认（H-4）** |
| S-8 | 数据库连接池 5 + WAL 单写者 | `lib-db/src/pool.rs`、`config.rs` | 未发现事务内 `await` 别的事；取连接超时 10s | 短查询为主 | **本轮不作为主因** |

### 3.2 H-1（主因候选）：测试进程 worker 被同步等待阻塞

证据链：

1. `crates/bin-tests/src/main.rs` 用 `Builder::new_multi_thread().enable_all()`，worker 数为核数；`cli::default_concurrency()` 取 `available_parallelism()`，本机 18。二者同阶，意味着「18 条用例各占一个 worker」时，任何一条用例阻塞 worker 都会直接压缩其它用例可用的执行线程。
2. `Harness::wait_until` 在 `async fn` 里被同步调用（`cases/tui/connection.rs` 的首轮回复等待、`cases/tui.rs` 的公共等待），内部是 `std::thread::sleep(POLL_INTERVAL)` 循环，直到条件成立或超时。
3. K-1 的失败画像与之一致：失败集合在不同次运行间变化（谁与 TUI 用例同批，谁被饿）；单跑全过；降并发全绿；失败耗时恰好压在用例内部等待上限（20s / 45s）。

结论：这不是服务端吞吐不足，而是**测试进程把异步等待写成了同步等待**。这也解释了为什么 `session.message`（本身 2.7s）能拖到 45s——它等的不是服务端，而是调度。

### 3.3 H-2（次因候选）：断连链全局串行 + 持会话锁跨 `await`

证据链：

1. `CHAIN` 让所有客户端的断连清理串行执行；每条清理里 `stop_session` 会「数据库条件更新 → `executor.stop`（最多等 5s）→ 写者收尾 flush」。
2. 取消类用例（`tui.esc_cancel` / `tui.ctrl_d_cancel`）与重连类用例（`tui.reconnect`）都会触发断连链；并发到达时后面排队的清理会被前面的 5s 级等待拖住。
3. 会话锁在 `clean` 里**跨 `await` 持有**，与占用 / 释放路径共用同一把锁，进一步放大排队。

结论：需要把「全局串行」收窄为「同一客户端串行」，并把「收尾等待」移出锁与链的关键路径（后台收尾 + 超时兜底），而不是加限流。

### 3.4 H-3 / H-4：需要指标才能定性的项

- H-3：全局 Run 许可 4 在共享服务端 + 18 条并发用例下是否是吞吐上限。判据不是「猜」，而是采集**排队时长**与**同时在跑数量**：若排队时长长期为 0，则许可不是瓶颈；若有明显排队而 CPU 空闲，则许可应在服务端侧按核数或按配置推导，而不是限制测试并发。
- H-4：注册表整表单锁与会话锁表膨胀。需要采集「写锁等待时长」与「`session_locks` 条目数」；若写锁等待可观测，再评估 `ArcSwap<Registry>`（读多写少、写时整表 clone）是否值得引入新依赖。**本轮不预设结论**。

### 3.5 本轮明确排除（不处置）

- `RunCancels` 的 `Mutex<HashMap>`：锁内只做内存读写，不跨 `await`。
- 下行通道：`try_send` + 容量 64，不阻塞事件写入；通道满按「流已废」处理是设计语义。
- SSE 帧合成与保活：`unfold` + `select!`，无锁、无阻塞。
- 心跳扫描（5s）与事件轮转（60s）：都在取快照后处理，轮转在阻塞线程池；与 45s 级超时不同阶。
- 数据库 WAL 与 `busy_timeout`：本轮不改存储参数，只在指标里记录取连接等待。

### 3.6 定位手段（先量测，再改）

| 手段 | 观察点 | 用途 |
|---|---|---|
| 结构化日志（`debug` / `info`） | Run 排队开始 / 结束、执行开始 / 结束、终态写入、断连链进入 / 退出、`stop_session` 各阶段、journal 单帧写入耗时（超过阈值才打） | 定位「慢在哪一段」 |
| 进程内指标快照（仅测试期，`bin-tests` 侧读取） | 同时 `RUNNING` Run 数、排队数、下行通道满次数、`session_locks` 条目数、断连链排队长度 | 判断是许可、锁还是通道 |
| 测试进程侧计数 | 每个用例阻塞 worker 的累计时长（`wait_until` / 同步调用点插桩） | 直接验证 H-1 |
| 对照实验 | 只改 H-1 后复跑；只改 H-2 后复跑；两者都改后复跑 | 分离主因与次因，避免「一起改、一起绿」 |

> 测试执行需要明确授权。未授权时，本阶段只允许做代码审查、静态检查与日志点审查，且不勾选任何以运行结果为准的判据。

## 五、技术方案

### 5.1 并发修复策略（顺序不可颠倒）

> **归因方式（Batch A 定稿）**：K-1 不可复现，因此不再用「改完失败数下降」证明收益。每个修复都用 P2.1-002 / 003 的指标做「修复前 / 修复后」对照（阻塞时长、清理链耗时、排队时长、锁表条目数），并说明该缺陷在默认并发下的实测量级。口径见 [`decisions.md`](decisions.md) 的 D-P2.1-007。

1. **量测**：先加日志与指标，在默认并发下取一轮基线（失败用例、耗时分布、指标快照）。
2. **修阻塞**：消除测试进程内的同步等待（H-1）。这一步预期解决大部分现象，必须单独跑一轮全量确认。
3. **解串行**：收窄断连链互斥范围、把收尾等待移出锁与链、治理会话锁表（H-2 / H-4）。每改一处单独回归。
4. **复核**：用指标判断全局 Run 许可与 journal 逐帧写入是否真的是瓶颈（P2.1-008），本步**只出结论、不动默认值**。任何并发数值或语法调整统一归 P2.1-015，且硬前置是本阶段的默认并发全量回归通过——否则无法区分「修复生效」与「默认值变相放宽」。

### 5.2 可观测性方案

- 日志沿用 `tracing`，新增点默认 `debug`，跨阈值（如单帧落盘 > 50ms、单次清理 > 500ms）升级 `warn` 并带关键 ID：`run_id` / `session_id` / `client_id`。
- 不在热路径做格式化开销：耗时用 `Instant::elapsed()` 后先比较阈值，再决定是否构造日志参数。
- 指标只在进程内聚合，不新增 HTTP 接口、不新增配置项；`bin-tests` 需要读取时通过已有观测入口（如运行时会话句柄）或进程内用例读取。

### 5.3 锁使用原则

| 场景 | 允许 | 禁止 |
|---|---|---|
| 纯内存短读写（注册表字段、取消表） | `std::sync::Mutex` / `RwLock`，锁内只做内存操作 | 锁内 `await`、锁内 IO、锁内 sleep |
| 需要跨 `await` 的互斥（会话级串行） | `tokio::sync::Mutex`，且临界区必须只包住必要步骤 | 把「收尾等待 / 重试 / 超时兜底」放进临界区 |
| 读多写少且需要整表快照 | 现方案「读锁取快照后放锁」；`ArcSwap` 仅在指标证明写锁争用时才评估 | 为了「看起来无锁」提前引入依赖 |
| 测试进程内的等待 | `tokio::time::sleep` + 轮询，或事件驱动等待 | 在 `async` 上下文里 `std::thread::sleep` / 阻塞 `recv` |

### 5.4 并发配置（`NC` 形式，P2.1-015）

- 语义：`max_concurrent_runs = "2C"` 表示 `2 × CPU 核数`；整数写法（`4`）语义不变。
- 默认值：`[agent]` 整段缺省或该字段缺省时为 `3C`（`Cores(3)`），核数由装配层取一次、运行期不变。
- 解析位置：值类型放 `types-core` 并提供 `resolve(cores)` 纯函数，装载与文案校验在 `lib-bin-cli`，`Semaphore` 只在 `agent-runtime` 装配时拿到最终数值。
- 边界：`0`、`0C`、非法后缀、负数、溢出都按配置错误处理并点名字段，不 panic、不产生超限信号量。
- 顺序：**先结案 G-1，再改默认值**。不允许用「默认值变大」掩盖未修好的并发问题。

## 八、已知限制与风险

1. **根因可能不止一个，而且本轮一个都复现不了**：Batch A 的默认并发 3 次 + 5 档加压实验全部全绿，H-1 ~ H-4 只能靠结构性证据与指标量级定级。报告里必须保留「每个假设的验证结论」，包括被否决的假设。
2. **日志本身会改变性能**：热路径日志必须阈值触发且不构造无谓字符串，否则会制造新的假象。
3. **断连链并行化的语义风险**：只允许把全局串行收窄为按客户端串行；「同一客户端的清理顺序」与「帧先于反注册」不能变。
4. **`ArcSwap` 不是结论**：它解决的是注册表整表单锁的读侧争用，代价是写路径整表 clone 与新依赖。指标未显示争用时引入它属于过度设计。
5. **归因混淆**：G-1 与 G-2 同时在改，全量回归前必须先完成 G-2 的 import 收敛；任何一轮红/绿都要能对应到唯一的改动集合。
6. **测试执行受授权约束**：P2.1-001 / P2.1-012 / P2.1-013 需要明确授权后才能执行；未授权时本阶段只能推进 A 的代码审查部分与 C 的位移。
7. **共享服务端仍是单进程单库**：即使修好串行点，SQLite 单写者仍是天花板；本阶段只保证「18 条用例并发下不出现 20s / 45s 级饥饿」，不承诺更高并发。
8. **默认值变更会放大上游并发**：`3C` 在本机 18 核时是 54；Mock 无压力，但真实 Provider 可能限流。P2.1-015 只改配置面，不承诺上游配额，报告里记录换算后的数值与风险。
9. **配置语法兼容性**：`"2C"` 引入字符串值，旧配置的整数写法必须继续可用；共享服务端仍走「不写 `[agent]` → 默认值」，因此默认值一改就影响全部用例的并发度，必须单独回归。
10. **`cases/` 仍有领域自有的探测与等待**：Batch C 只把 Mock 替身与通用支持移出 `cases/`（D-P2.1-013）。`cases/web/*` 的静态资源 / 预检探测、`cases/{occupancy,runtime,disconnect}.rs` 的单点 HTTP 断言，以及 `cases/{persist,run,probe}.rs` 的少量轮询循环仍在用例内——它们各自只服务一个用例（或一个领域内的用例族），本轮按「只做位移」未外移。因此 G-2-1 的「`cases/` 不出现 HTTP/SSE 探测」只在本批次清单范围内成立；若要完全满足，需要另开任务把领域探测 helper 也归入 `util/`。
