## D-P2.1-007 G-1 的口径改为「结构修复 + 指标对照」

- **状态**：`DECIDED`（2026-11-21）
- **问题**：P2.1 的 G-1 原本以「默认并发下 `--all` 会失败」为前提，判据是「修完失败数下降」。这个前提还成立吗？
- **背景与证据**：
  - 默认并发（18）连续 3 次 `--all` 全部通过（73/73，预热墙钟 34.0s / 34.1s / 34.0s），失败数为 0。
  - 对照：`--all --concurrency 4` 同样全绿且墙钟相同（33.9s）。把并发压到 4 既不能让全量变快也不能变慢，说明不存在「共享服务端排队」这一路径。
  - 加压：6 / 18 / 36 个 CPU 忙循环、14 条 TUI 全并发、4 路大文件写，五档负载全部 0 失败；2× 超订下墙钟翻倍到 74.2s，仍全绿。
  - K-1 记录里的画像（`session.message` 44.5s 失败、`tui.reconnect` 20.0s 失败）与当前代码对不上：`session.message` 现在 221ms，`tui.reconnect` 15.1s 通过。
  - 证据文件：[`docs/reports/p2.1-001-baseline.md`](../../docs/reports/p2.1-001-baseline.md)。
- **可选方案**：
  1. 继续为「复现失败」投入，把压力加到复现为止；
  2. 承认不可复现，G-1 改为修「已由代码与指标确认存在的结构性缺陷」，用指标对照代替失败数；
  3. 直接关闭 G-1，只做 G-2 / G-3。
- **决策**：②。G-1 改名为「结构性并发缺陷修复」，判据重写为 README §七 的 G-1-1 ~ G-1-6：
  - 默认并发连续 3 次全绿降级为**回归**判据；
  - 每个缺陷必须有「修复前 / 修复后」指标对照；
  - K-1 的最终口径（未复现 + 环境因素未排除）必须可查。
- **理由**：③（直接关闭）会丢掉确实存在的结构缺陷（`async` 上下文里的同步等待、全局断连链互斥、锁表只增不减）；①没有收敛条件，五档加压已经证明 CPU / 磁盘压力不是触发条件。②保留可验证的收益，且不依赖「运气」。
- **约束**：仍然禁止测试侧限流；仍然不允许用「调大默认并发」当收益。
- **承接任务**：P2.1-004 ~ P2.1-008、P2.1-013。

## D-P2.1-008 指标采集放在 `metrics` 特性下，由测试报告输出

- **状态**：`DECIDED`（2026-11-21）
- **问题**：进程内指标（Run 排队、清理链、`stop` 四阶段、journal 单帧、下行丢弃、锁表条目、取连接等待）怎么落地才算「不为排查污染正式构建」？
- **可选方案**：
  1. 常驻编译：正式构建也带指标与阈值日志；
  2. 用 `#[cfg(feature = "metrics")]` 隔离：正式构建是空实现，测试构建（`make test`）打开；
  3. 只在 `bin-tests` 里做，服务端不采集。
- **决策**：②。特征名 `metrics`，链路为 `bin-agent → lib-bin-web → {agent-runtime, manager-agent} → lib-db`；`bin-tests` 直接依赖 `manager-agent/metrics`。`Makefile` 的 `test` 目标用 `--features metrics` 构建 `bin-agent`，`build` / `release` 不带。指标不再打到标准输出，改为写进测试报告的「观测数据」一节（`target/tests/<run>/README.md`），同时在跨阈值时打 `debug` / `warn` 日志。
- **理由**：③做不到——指标发生在服务端进程里，`bin-tests` 采不到；①会让正式构建付采集与日志判断的代价，且 `warn` 阈值日志会进入生产日志。②同时满足「正式构建零代价」与「测试侧可读」。
- **代价与已知限制**：
  - 测试构建与正式构建是两套产物，`make test` 首次会多一次重编译；
  - `bin-tests` 报告里的指标只覆盖**测试进程内装配**的运行时；共享 / 隔离用例的服务端是子进程（`Server::stop` 为 `start_kill`，没有优雅关闭路径），它们的指标只能从各自的 `server.log` 按阈值行汇总。
  - 测试服务端默认 `--log-level warn`，`debug` 级阈值（如 100ms 排队）只在 `trace` / `debug` 级的服务端可见（如 `run.concurrency`）。
- **承接任务**：P2.1-003（已完成）、P2.1-008。

## D-P2.1-009 `lib-db` 引入可选依赖 `tracing`

- **状态**：`DECIDED`（2026-11-21）
- **问题**：取连接（`Database::begin`）的等待时长需要在超过阈值时打日志，但 `lib-db` 原本没有日志依赖。`README.md` §五 第 5 条要求「依赖不扩散，新增依赖需 D-P2.1-001 决策」。
- **可选方案**：
  1. 不加依赖，只做内存累加，由 `manager-agent` 的快照带出（Batch A 初版做法）；
  2. 加可选依赖 `tracing = { optional = true }`，由 `metrics` 特性启用；
  3. 把取连接计时挪到 `manager-agent`。
- **决策**：②。`tracing` 是 workspace 已有依赖（同版本、同来源），不是新引入的第三方框架；声明为 `optional`，只在 `metrics` 特性下编译。
- **理由**：①的缺口是「子进程服务端的取连接等待只能靠快照，偏偏子进程的快照读不到」——一旦连接池真的饱和，日志是唯一现场；③会让 `lib-db` 的等待与调用方的实现耦合，且 `begin` 在 `lib-db` 内部是唯一事务入口。
- **判据**：正式构建（不带 `metrics`）的 `lib-db` 依赖树里不出现 `tracing`；`cargo tree -p lib-db` 可核。
- **承接任务**：P2.1-003（已完成）。

## D-P2.1-010 锁面口径：互斥原语不 ArcSwap 化，整表状态先拆每帧写锁

- **状态**：`DECIDED`（2026-11-21）
- **问题**：P2.1-008.1 要求逐处判断「同步锁能否换成 `ArcSwap` 或其他无锁方式」。哪些项属于「锁在提供语义」，哪些只是「数据交接」，需要先定口径，否则会把互斥改成自研互斥。
- **背景与证据**：清单与逐项结论见 [`docs/reports/p2.1-008.1-lock-audit.md`](../../docs/reports/p2.1-008.1-lock-audit.md)。进程内 12 处同步原语，**只有 `RuntimeState::inner`（整表 `RwLock`）落在每帧事件路径上**（`Downlink::forward` 每帧取一次写锁）；会话锁、客户端串行锁、TUI 连接状态机提供的是「同一会话 / 同一客户端串行」语义；`journal` 的 `Mutex` 在 `spawn_blocking` 内只覆盖一次 `append` / `flush`，P2.1-008 已测单帧最长 0ms。
- **可选方案**：
  1. 全面无锁化：把所有 `Mutex` / `RwLock` 换成 `ArcSwap`；
  2. 按用途分类：互斥原语保留，快照类逐项评估，整表状态先拆热路径再评估；
  3. 一律不改，只记录结论。
- **决策**：②。
  - **互斥原语不 ArcSwap 化**：`session_locks`、`CHAINS`、`LinkState` 的串行语义是需求本身，替换只会变成自研互斥。
  - **快照类逐项评估**：`LinkSnapshot` 技术上适用，但读侧不在 UI 刷新路径（只有 `shutdown` 与用例读），无可观测收益 → 不改。
  - **整表状态先拆热点**：`Registry` 直接换 `ArcSwap` 等于把写锁换成整表 clone；必须先拆掉「每帧取写锁」（通道表独立快照 + 序号改原子），再按数据判断是否还值得。
  - **阻塞线程内短锁**：`journal` 的出路是「单写者 + 频道」结构，不是换锁类型。
- **理由**：①会把「必要串行」和「无谓争用」混为一谈，且给每个互斥点引入正确性风险；③无法回答「整表锁到底有没有排队」，因为缺的正是观测口径。
- **约束**：
  - 任何锁改造的前置是**数据**：`metrics` 特性下新增的「注册表整表锁 / 下行转发 / 取会话锁等待」三组指标，已在 P2.1-008.1 生成两轮基线（见报告 §四）。
  - **一次只改一处**，改完单独跑一轮全量并留前后对照（沿用 Batch B 的规则）。
  - 语义零变化清单：同会话串行、断连顺序（`client_closed` → 反注册 → 停运行时会话 → 撤回占用）、事件先落盘 flush 再转发、锁内不跨 `await`。
  - 测试侧串行夹具（`bin-tests` 的共享服务端锁、`app_home` 锁、Mock 记录锁）不在范围内。
- **实测与结论**（2026-11-21，授权跑两轮）：`runtime tui` 32/32、`--all` 73/73 全绿；注册表整表锁读 131 / 138 次、写 296 / 307 次，**最长等待均为 0ms**；下行转发 99 / 100 帧，**单帧最长 0ms**；取会话锁等待 20 / 22 次全为 0ms；100ms 阈值 `warn` 零触发（含共享服务端子进程的 `server.log`）。按本决策的口径，**逐项结论为「不改」**，§五 的候选改造不实施，只保留为「出现毫秒级等待」时的处置路线。
- **承接任务**：P2.1-008.1（已完成）。

## D-P2.1-012 表级快照的形态与启用口径

- **状态**：`DECIDED`（2026-11-21，当前**不启用**）
- **问题**：P2.1-008.2 要求评估「内存持有整表 `ArcSwap` 快照、写后发通知由消费者重读」能否消除读放大。形态怎么定、现在是否落地？
- **背景与证据**：[`docs/reports/p2.1-008.2-db-read-cache.md`](../../docs/reports/p2.1-008.2-db-read-cache.md)。执行期 10 类数据库访问全部落在 API 请求上（每次 1~2 条语句）；事件转发、心跳扫描、断连标记、事件落盘等高频路径零 SQL；前端只有 chat 页，TUI 按需调用，`probe.health` 只在连接 / 重连各一次；整轮全量「取数据库连接」仅 3 次。**没有读路径同时满足「高频 + 可陈旧 + 非权威」**。
- **可选方案**：
  1. 预取式：写后发布通知，消费者立即重读 DB 并替换快照（任务最初设想的形态）；
  2. 失效式：写后发布通知 → 快照打脏 → 下一次读回源并替换；
  3. 不实现，只把口径写死，等出现真实读放大再落地。
- **决策**：**口径取 ②，落地取 ③**。
  - 形态固定为「失效 + 读时回源」：没有读放大时，预取式把「每次读一条查询」变成「每次写一次查询」，写完立刻读回也与读时回源等价，还多一个常驻消费者与生命周期管理。
  - 当前不落地：没有客户端需要缓存，按「不写投机性代码」的原则不预实现。
- **口径约束**（启用时必须照做，偏离需重新登记）：
  - 快照放 `service-core`（`repository` 只允许被本 crate 的 Service 调用，`AGENTS.md` 第 7 条）；通知类型放 `types-core`；订阅与刷新任务放装配层 `manager-agent`。
  - 走 `framework-bus` 的纯通知语义（不带数据、边沿触发、可合并）；先 `watch` 再全量加载。
  - 读侧 `load_full()` + `Arc::clone`，无锁；同一张表回源单飞；回源失败保留旧快照 + `warn`。
  - **权威判定读一律不缓存**：取消、终态条件更新、执行期状态一律直读数据库（D-P2-029 / D-P2-030）。
  - 可观测项（命中 / 回源 / 刷新耗时）只在 `metrics` 特性下采集（D-P2.1-008）。
- **触发条件**：出现轮询型调用方；或某只读 API 的读频次显著高于写频次且单次语句进入毫秒级；或 `session/list` 的相关子查询成为可观测成本（后者应先考虑报告 §七 的两条 SQL 改造，而不是缓存）。
- **承接任务**：P2.1-008.2（已完成，结论「不改」）。

## D-P2.1-011 `arc-swap` 的引入范围

- **状态**：`DECIDED`（2026-11-21）
- **问题**：`arc-swap` 已在 workspace（`Cargo.toml` 的 `arc-swap = "1.8"`，`lib-core` 的 `directorys` 已在用）。判断锁面时是否可以为了「随时可换」先把它加到 `manager-agent` / `service-core` / `lib-bin-tui`？
- **可选方案**：
  1. 先加依赖，等决定改造时直接用；
  2. 只在确定改造时，与实际改动一起引入，并在同一次改动里说明用在哪一层；
  3. 一律不用，只保留 `lib-core` 现有的那一处。
- **决策**：②。`arc-swap` 是 workspace 内已有依赖，不属于新增第三方库；但**新增到某个 Crate 仍算扩展依赖**（`README.md` §五 第 5 条），必须在决定改造的同一处改动里登记「用在哪、为什么不放 `lib-core`」。
- **理由**：①会让依赖面先于结论铺开，后续若判定「不改」就留下无用的依赖边；③排除了 P2.1-008.2 可能需要的表级快照形态（`service-core` 侧持有 `ArcSwap<Vec<..>>`）与 §五 的通道表快照。
- **判据**：`cargo tree -p <crate> | grep arc-swap` 只应出现在确实做了改造的 Crate 上；`lib-core` 保持「基础设施才用」的定位，不为业务缓存提供依赖转发。
- **承接任务**：P2.1-008.1（本轮未引入）、P2.1-008.2（若采用表级快照）。
