## K-1 `make test ARGS="--all"` 默认并发下共享分片超时

- **状态**：已结案（2026-11-21，P2.1 Batch A）——**默认并发下未复现**，不再按「复现失败」处置；确认存在的结构性问题转入 P2.1-004 ~ 008（见下方「P2.1 Batch A 复核」与 `decisions.md` D-P2.1-007）
- **发现时间**：2026-11-21，P2 Batch E（P2-019 / P2-020）验收
- **现象**：默认并发跑全量用例时，`shard-shared` 里少数长耗时用例报「未在 N 秒内收到回复」「下行流未收到 `run_completed`」，耗时恰好压在各自的内部等待上限（20s / 44.5s），用例判定失败。
- **默认并发度**：`crates/bin-tests/src/cli.rs` 的 `default_concurrency()` 取 `available_parallelism()`，本机为 18，即 18 条用例同时打同一个共享服务端（`shard-shared`），另有 isolated 用例各自起子进程。
- **复现与观测**：

| 命令 | 结果 |
|---|---|
| `make test ARGS="--all"`（第 1 次） | 57 条中 2 失败：`tui.reconnect`（20.0s）、`session.message`（44.5s） |
| `make test ARGS="--all"`（第 2 次） | 57 条中 2 失败：`session.message`（44.5s）、`tui.esc_cancel`（20.0s） |
| `make test ARGS="session tui"`（并发 18） | 18 条中 3 失败：`tui.ctrl_d_cancel`、`tui.reconnect`、`session.message` |
| `make test ARGS="session tui --concurrency 4"` | 18 条全通过（`session.message` 2.7s、`tui.reconnect` 15.1s） |
| `make test ARGS="session.message"` 单跑 | 通过（2.7s） |
| `make test ARGS="tui.reconnect"` 单跑 | 通过（15.1s，距 20s 上限仅 5s 余量） |
| `make test ARGS="--all --concurrency 4"` | **57 条全通过**（含 `web.ui` 28 项、`web.e2e` 3 条） |

- **判断**：与任何功能代码改动无关——两次 `--all` 的失败集合不同、同一用例单跑即过、降并发即全绿，失败集中在共享服务端上的长耗时用例，属**并发度导致的等待超时**，不是断言或业务行为错误。P2 Batch E 的新增 crate（`agent-context-core` / `agent-context`）未进入 `bin-agent` 依赖图，也不在失败链路上。
- **余量问题**：`tui.reconnect` 单跑 15.1s，本身已贴近 20s 上限，并发一高必然先崩；`session.message` 的 44.5s 同样是等满上限后失败，说明这两条用例的等待预算对「共享服务端 + 高并发」没有余量。
- **影响**：全量验收只能用低并发跑；CI 或他人本地用默认并发跑 `--all` 会看到与改动无关的红灯，容易误判为回归。
- **处置方向（本阶段定稿，未实施）**：
  1. 给 `bin-tests` 的默认并发加机器相关上限（例如 `min(核数, 4~8)`），或让共享分片单独限流；
  2. 或把这几条长耗时用例的内部等待上限从 20s / 45s 上调，并在用例名或报告里标注「依赖共享服务端」；
  3. 或在报告里显式记录本次并发度与「高并发下的已知抖动」，让红灯可归因。
  - 三条互不冲突，倾向第 1 条 + 第 3 条：限流治本，记录治标。
- **验收口径**：本项结案时需给出「默认并发下 `make test ARGS="--all"` 稳定全绿」的证据（连续多次运行），或明确改为「验收固定用低并发 + 报告标注」，二者择一写死。

### P2.1 Batch A 复核（2026-11-21）

复核时用例总数已从 57 条增至 73 条（`874c43b` P2 验收补齐 `llm.canary` / `persist.*` / `run.*`），机器为空闲状态。

| 运行 | 并发度 | 结果 | 墙钟耗时 |
|---|---|---|---|
| `--all` × 3（默认） | 18 | 73/73 通过，失败 0，三次一致 | 46.6s（首跑）/ 34.1s / 34.0s |
| `--all --concurrency 4` | 4 | 73/73 通过 | 33.9s |
| `session tui`（本问题最集中的组合） | 18 | 19/19 通过 | 16.5s |
| 6 个 CPU 忙循环 + `--all` | 18 | 73/73 通过 | 34.0s |
| 18 个 CPU 忙循环（核心饱和）+ `--all` | 18 | 73/73 通过 | 37.1s |
| 36 个 CPU 忙循环（2× 超订）+ `--all` | 18 | 73/73 通过 | 74.2s |
| 18 个忙循环 + `tui --concurrency 14` | 14 | 14/14 通过 | 17.3s |
| 4 路顺序大文件写 + `--all` | 18 | 73/73 通过 | 34.1s |

关键反差：

- `session.message` 现在是 **221ms**（本问题记录为 44.5s 失败 / 2.7s @ 并发 4），离 20s 上限两个数量级。
- `tui.reconnect` 仍是 15.1s 且通过，是本轮唯一贴近上限（20s）的用例。
- 并发 4 与并发 18 的墙钟耗时相同（33.9s vs 34.0s），「并发度高导致排队」这一解释路径不成立。
- 加压只让耗时整体上浮（2× 超订下 74.2s，最长用例变成 `web.e2e` 50.4s / 60s），**从未出现「耗时精确压在某条用例内部上限」的等待型超时**，与本问题记录的失败形态不符。

复核结论：

1. 本问题在当前代码上**不可复现**，无法作为「修完失败数下降」的判据来源。
2. 不能仅归因为「运气好」：失败形态（精确压线）与加压结果（整体上浮）特征不同，更可能是当天环境因素（`make release` 全量构建、`pnpm`、Playwright、杀软对临时目录的扫描同时进行），这一点事后无法用代码复现，**只能记为未定性**。
3. 原「处置方向」三条全部作废：第 1 条属测试侧限流（`README.md` §二 明令禁止），第 2 条是用放宽上限掩盖症状。
4. 确实存在的**结构性缺陷**另有其事，已量化为独立任务：`async` 上下文里的同步等待（P2.1-004，实测累计 4.8s / 34s）、全局断连链互斥（P2.1-005，实测并发水位 2、最长 15ms）、收尾等待跨锁（P2.1-006）、会话锁表只增不减（P2.1-007，见 K-2）。
5. 证据全文：`docs/reports/p2.1-001-baseline.md`、`docs/reports/p2.1-002-blocking-audit.md`、`docs/reports/p2.1-003-observability.md`。

## K-2 会话锁表只增不减

- **状态**：已结案（2026-11-21，P2.1-007）——取锁改走读锁快路径；会话停止 / 占用释放后在无其它持有者时回收条目
- **发现**：2026-11-21，P2.1 Batch A 的可观测性改造（P2.1-003），原为 README §3.5 的假设 H-4
- **现象**：`crates/manager-agent/src/runtime/registry.rs` 的 `session_locks: HashMap<String, Arc<Mutex<()>>>` 只 `entry().or_default()` 插入，**从不删除**；取锁每次都走注册表的**写锁**，与全部读操作争用。
- **实测**（进程内用例，默认并发 18）：建过 6 个会话后表内 6 条，终态快照 2 条——条目数与历史会话数同向单调增长；同一轮里清理链最长 15ms、并发水位 2，**尚未观测到锁竞争**。
- **影响**：长跑进程内存随历史会话数单调增长；每次取锁都要写锁，理论上会与客户端 / 占用 / 通道的读操作排队。
- **处置方向**：P2.1-007——取锁先走读锁快路径，未命中再降级写锁插入；会话停止 / 占用释放后在无其它持有者时回收条目（`Arc::strong_count` 或显式引用计数），回收失败只记 `debug`。
- **验收口径**：长跑后条目数不随历史会话数单调增长；同一会话的取锁仍唯一；`runtime.occupancy` / `runtime.handler` 通过。
- **证据**：`docs/reports/p2.1-003-observability.md`。

- 证据：`docs/reports/p2.1-007-lock-reclaim.md`。
