# P1 验收标准

所有条目必须**可客观验证**：有明确命令、明确期望输出、明确失败判据。验收时逐条记录“通过 / 不通过 + 证据”。

**P1 不存在“看起来能用就算通过”。**

---

## 1. Build 验收

| 编号 | 检查项 | 判据 |
|------|--------|------|
| B-1 | Debug 构建 | `cargo build` 退出码 0，无 error |
| B-2 | 格式检查 | `cargo fmt --check` 退出码 0 |
| B-3 | 静态检查 | `cargo clippy --all-targets` 无 error；warning 需逐条说明或清零 |
| B-4 | 依赖去重 | `cargo tree -d` 中不存在同一 `framework-*` crate 的多版本共存 |
| B-5 | 工具链固定 | 干净环境（无预设环境变量）下，`rustc --version` 与 `rust-toolchain.toml` 一致 |
| B-6 | 前端静态类型 | WebUI 的类型检查命令退出码 0（不得依赖 `skipLibCheck` 掩盖 SDK 类型错误） |

## 2. Server 验收

| 编号 | 检查项 | 判据 |
|------|--------|------|
| S-1 | 启动 | `agent server` 打印 `listening on <addr>`，进程存活 |
| S-2 | 健康检查 | `curl <addr>/<health 端点>` 返回 200 且包含版本、启动时间字段 |
| S-3 | 端口占用 | 占用端口后启动，退出码非 0 且错误信息包含被占用端口 |
| S-4 | trace id | 请求带 `x-trace-id: test-123` 时响应头回显 `test-123`；不带时响应头出现服务器生成的 id |
| S-5 | 统一错误结构 | 参数错误 / 404 / 内部错误三类响应均为 HTTP 状态码 + `{code, message}` 结构，字段名一致 |
| S-6 | 错误不泄漏 | 触发 panic 的路径产生的响应体不含 panic 文本、文件路径、堆栈 |
| S-7 | 日志可用 | 一次请求在日志中可定位到 trace id 与处理结果 |
| S-8 | 优雅关闭 | Ctrl+C 后进程在 5s 内退出，日志含关闭过程；无“半条”SSE 事件残留 |
| S-9 | 关闭期拒新请求 | 关闭过程中新请求得到可读错误而非静默断连 |
| S-10 | CORS | 允许来源的预检与实请求通过；非允许来源被拒绝（不返回通配 `*`） |

## 3. TUI 验收

| 编号 | 检查项 | 判据 |
|------|--------|------|
| T-1 | 默认进入 | 无参数运行 `agent` 进入 TUI；`agent tui` 行为一致 |
| T-2 | 基本闭环 | 输入并发送消息后，界面出现流式增长的助手回复，最终状态为完成 |
| T-3 | 输入不阻塞 | 流式输出期间按键有响应（可切换到输入框继续输入） |
| T-4 | 中断 | `Esc` 中断后界面回到可输入状态，Server 侧该 Run 状态为已取消 |
| T-5 | 启动时 Server 未运行 | 不崩溃、不退出；显示服务地址与错误原因，并提供重试操作 |
| T-6 | 运行中断线 | 保留已收到的内容并标注“连接中断”，不出现空白覆盖或 panic |
| T-7 | 终端恢复 | 退出后无残留 raw mode / alternate screen / 隐藏光标 |
| T-8 | 全部走 SDK | 客户端代码检索不到除探活外的裸 path 字面量 |

## 4. WebUI 验收

| 编号 | 检查项 | 判据 |
|------|--------|------|
| W-1 | 可访问 | 浏览器打开 Server 地址可加载页面，无控制台 error 级错误 |
| W-2 | 基本闭环 | 发送消息后可见流式输出，结束后可继续发送 |
| W-3 | SDK 接入 | 页面请求全部命中生成 SDK 定义的 path；前端源码中无手写 API path 字面量 |
| W-4 | 错误呈现 | Server 关闭时页面显示可读错误提示，不白屏、不无限转圈 |
| W-5 | CORS 生效 | 浏览器直连 Server 的请求未被 CORS 拦截，且不存在 `*` 通配放行 |
| W-6 | 静态资源 | 刷新任意前端路由（SPA 路径）仍返回页面；未知 API 路径返回 API 404 结构 |

## 5. SDK 生成验收

| 编号 | 检查项 | 判据 |
|------|--------|------|
| G-1 | 单命令生成 | 一条命令同时产出 TS SDK 与 Rust SDK，无手工中间步骤 |
| G-2 | 接口一致 | 两份 SDK 的接口集合（name + method + path）完全一致，无一侧缺失 |
| G-3 | 类型可编译 | 生成的 Rust SDK `cargo build` 通过；生成的 TS SDK 类型检查通过 |
| G-4 | 幂等 | 连续执行两次生成，第二次无文件变更（`git status` 干净） |
| G-5 | 非法元数据防护 | 构造重名接口 / 重复 method+path，生成器以非 0 退出并给出可定位的错误信息 |
| G-6 | 唯一来源 | 仓库中不存在第二份人工维护的 API 定义（无手写 OpenAPI、无前端手写接口表） |
| G-7 | 生成物标记 | 生成文件头部含“自动生成，勿手改”标识 |

## 6. API 一致性验收

| 编号 | 检查项 | 判据 |
|------|--------|------|
| A-1 | 变更可检测 | 修改任一 API 定义后不重新生成，运行一致性检查命令以非 0 退出 |
| A-2 | 提示可操作 | 失败输出包含“请运行 <命令> 重新生成”的明确指引与差异摘要 |
| A-3 | 重新生成后通过 | 执行生成后检查退出码 0 |
| A-4 | 本地与 CI 等价 | 本地执行与 CI 执行使用同一条命令 |
| A-5 | DTO 一致 | 同一 DTO 在 TS 与 Rust 两侧字段名、可选性一致；`i64` 类 id 的表示差异已被显式约定（TS `string` / Rust `i64`） |

## 7. SSE 验收

| 编号 | 检查项 | 判据 |
|------|--------|------|
| E-1 | 事件格式 | `curl -N <stream endpoint>` 输出符合 SSE 规范（`event:` + `data:`，事件间空行分隔） |
| E-2 | 事件序列 | 序列为 `run_started` → N × `message_delta` → `run_completed`，顺序正确 |
| E-3 | 心跳 | 空闲期间按约定间隔出现 `heartbeat` 事件 |
| E-4 | 错误事件 | 构造失败场景时收到 `run_failed`（含可读 message），流正常结束而非挂死 |
| E-5 | 客户端断开 | 中途断开 `curl` 后，服务端无 panic，相关任务被清理（日志可证） |
| E-6 | 关闭联动 | Server 关闭时进行中的流收到终止事件或明确断开 |

## 8. Single Binary 验收

| 编号 | 检查项 | 判据 |
|------|--------|------|
| X-1 | 单文件运行 | 仅拷贝 release binary 到干净目录（无静态资源目录、无前端产物），可启动 server |
| X-2 | 三种模式 | 同一 binary 支持 `agent`（TUI）、`agent server`、`agent run`、`agent status` |
| X-3 | WebUI 内置 | 上述干净目录环境下浏览器可打开 WebUI |
| X-4 | 帮助与版本 | `--help` / `--version` 正常，退出码 0 |
| X-5 | 基线记录 | binary 体积与冷启动时间已记录，并注明平台、构建 profile、测量方式 |
| X-6 | 无外部运行时 | 运行不依赖已安装的 Rust/Node/Python 运行时 |

## 9. 基础测试验收

> 本节仅在用户明确要求执行测试时进行；P1 本身不强制 AI 主动运行测试。

| 编号 | 检查项 | 判据 |
|------|--------|------|
| R-1 | 错误码契约 | 有覆盖 `ApiError` 映射的用例，参数错误 / 404 / 内部错误各至少一例 |
| R-2 | 会话隔离 | 有用例证明两个会话的消息互不可见 |
| R-3 | SSE 事件契约 | 有用例验证事件序列与结束条件（含失败事件） |
| R-4 | SDK 生成 | 有用例验证生成器对非法元数据返回错误、对合法输入幂等 |
| R-5 | 客户端错误分支 | 有用例覆盖“服务未启动”“超时”“非 2xx”三类客户端错误 |

```text

|------|------|------------------------------------------|
| S-1  | 通过 | `agent server` → listening on 127.0.0.1:20100 |
```

**任一 B/S/T/W/G/A/E/X 类条目不通过，P1 不视为完成**；第 9 类（基础测试）中除用户明确要求外，可按“未执行 + 原因”记录，不阻塞 P1。
